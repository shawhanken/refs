# 存储成本深度分析：字节码 vs 源代码

**文档版本**: 1.0  
**创建日期**: 2026-01-22  
**目的**: 澄清存储成本的真实差异

---

## 📋 执行摘要

**核心结论**：从**单次存储**的角度，字节码和源代码的存储成本**相近**。真正的差异在于：
1. **多版本累积成本**（升级场景）
2. **压缩率差异**
3. **元数据开销**
4. **迁移成本**（误认为是存储成本）

---

## 🔍 第一部分：单次存储成本对比

### 1.1 数据大小分析

#### EVM 字节码

**组成**：
```
EVM 字节码 = 操作码序列 + 数据（常量、字符串等）

示例（简单合约）：
- Solidity 源代码：~500 bytes
- EVM 字节码：~1-2 KB
- 比例：字节码 ≈ 2-4× 源代码
```

**特点**：
- 二进制格式，紧凑
- 包含所有常量（字符串、数字等）
- 包含函数选择器、事件签名等

#### PVM 字节码（marshal 格式）

**组成**（从代码分析）：
```rust
// crates/compiler-core/src/marshal.rs
CodeObject 序列化包含：
- instructions: Vec<CodeUnit>  // 指令序列
- locations: Vec<SourceLocation>  // 行号信息
- constants: Vec<ConstantData>  // 常量（字符串、数字等）
- names: Vec<String>  // 名称表
- varnames: Vec<String>  // 变量名
- cellvars, freevars: Vec<String>  // 闭包变量
- linetable: Vec<u8>  // 行号表
- exceptiontable: Vec<u8>  // 异常处理表
- source_path, obj_name, qualname: String  // 元数据
```

**特点**：
- 包含源代码位置信息（行号表）
- 包含完整的常量池
- 包含异常处理信息
- 可能比源代码更大（因为包含元数据）

#### Python 源代码

**组成**：
```
纯文本格式：
- 代码逻辑
- 注释（可选）
- 字符串字面量
- 数字字面量
```

**特点**：
- 文本格式，可读性强
- 可能包含注释（增加大小）
- 通常比编译后的字节码更紧凑（无元数据）

### 1.2 实际大小对比

#### 示例 1：简单函数

**Python 源代码**：
```python
def add(a, b):
    return a + b
```
- 源代码：~30 bytes

**PVM 字节码**（marshal 序列化）：
```
- instructions: ~20 bytes
- constants: ~10 bytes
- names: ~10 bytes
- locations: ~10 bytes
- 其他元数据: ~20 bytes
总计：~70 bytes
```
- 字节码：~70 bytes（约 2.3× 源代码）

#### 示例 2：中等复杂度 Actor

**Python 源代码**：
```python
@actor
class MyActor:
    def __init__(self):
        self.balance = 0
    
    def deposit(self, amount):
        self.balance += amount
        return self.balance
```
- 源代码：~150 bytes

**PVM 字节码**（估算）：
```
- instructions: ~100 bytes
- constants: ~50 bytes
- names: ~50 bytes
- locations: ~50 bytes
- 其他元数据: ~50 bytes
总计：~300 bytes
```
- 字节码：~300 bytes（约 2× 源代码）

#### 示例 3：复杂合约（EVM）

**Solidity 源代码**：
```solidity
contract ERC20 {
    mapping(address => uint256) public balanceOf;
    function transfer(address to, uint256 amount) public {
        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
    }
}
```
- 源代码：~200 bytes
- EVM 字节码：~2-3 KB（包含 ABI、选择器等）

### 1.3 单次存储成本结论

| 类型 | 源代码大小 | 字节码大小 | 比例 |
|------|-----------|-----------|------|
| **简单函数** | ~30 bytes | ~70 bytes | 2.3× |
| **中等 Actor** | ~150 bytes | ~300 bytes | 2× |
| **复杂合约** | ~200 bytes | ~2-3 KB | 10-15× |

**结论**：
- ✅ **字节码通常比源代码大 2-3 倍**（PVM）
- ⚠️ **EVM 字节码可能大 10-15 倍**（包含 ABI 等）
- ⚠️ **但差异不是数量级的**（都在 KB 级别）

## 💰 第二部分：区块链存储成本

### 2.1 存储成本计算

#### 以太坊存储成本（参考）

```
SSTORE 操作：
- 首次写入：20,000 gas
- 修改：5,000 gas（如果从非零改为非零）
- 清零：-15,000 gas（退款）

存储大小：
- 每个 slot：32 bytes
- 1 KB 数据 ≈ 32 slots
- 成本：32 × 20,000 = 640,000 gas
```

#### 实际存储成本对比

**场景 1：存储 1 KB 数据**

| 方案 | 数据大小 | Slots | Gas 成本 |
|------|---------|-------|----------|
| **源代码** | 1 KB | 32 | 640,000 gas |
| **字节码** | 2 KB | 64 | 1,280,000 gas |
| **差异** | 1 KB | 32 | 640,000 gas |

**结论**：字节码存储成本确实**高 2 倍**（如果字节码是源代码的 2 倍）

### 2.2 压缩率分析

#### PVM 字节码压缩

从代码中看到，PVM 使用 **LZ4 压缩**：

```rust
// crates/compiler-core/src/frozen.rs
impl FrozenCodeObject<Vec<u8>> {
    pub fn encode<C: Constant>(code: &CodeObject<C>) -> Self {
        let mut data = Vec::new();
        marshal::serialize_code(&mut data, code);
        let bytes = lz4_flex::compress_prepend_size(&data);  // LZ4 压缩
        Self { bytes }
    }
}
```

**压缩效果**：
- 源代码：文本格式，压缩率 ~50-70%
- 字节码：二进制格式，压缩率 ~30-50%

**压缩后大小对比**：

| 类型 | 原始大小 | 压缩后大小 | 压缩率 |
|------|---------|-----------|--------|
| **源代码** | 1 KB | ~300-500 bytes | 50-70% |
| **字节码** | 2 KB | ~1-1.4 KB | 30-50% |

**结论**：压缩后，字节码仍然比源代码大，但差异缩小。

## 🔄 第三部分：多版本存储成本（关键差异）

### 3.1 升级场景分析

#### EVM：不可升级模式

```
部署 v1：
  字节码 v1：2 KB → 存储成本：1,280,000 gas

需要升级：
  部署新合约 v2：
    字节码 v2：2 KB → 存储成本：1,280,000 gas
    旧合约 v1：仍然占用存储（无法删除）
  
总存储成本：2 × 1,280,000 = 2,560,000 gas
```

**特点**：
- ✅ 单次存储成本固定
- 🔴 升级需要部署新合约
- 🔴 旧合约无法删除（占用永久存储）

#### PVM：可升级模式（源代码存储）

```
部署 v1：
  源代码 v1：1 KB → 存储成本：640,000 gas

升级到 v2：
  替换源代码 v1 → v2：1 KB → 存储成本：5,000 gas（修改）
  
总存储成本：640,000 + 5,000 = 645,000 gas
```

**特点**：
- ✅ 单次存储成本低
- ✅ 升级只需修改（低成本）
- ✅ 旧版本不占用存储

#### 混合方案：版本化字节码存储

```
部署 v1：
  字节码 v1：2 KB → 存储成本：1,280,000 gas

升级到 v2：
  字节码 v2：2 KB → 存储成本：1,280,000 gas
  字节码 v1：保留（向后兼容）
  
总存储成本：2 × 1,280,000 = 2,560,000 gas
```

**特点**：
- ⚠️ 单次存储成本高
- ✅ 升级需要新版本（但可保留旧版本）
- ⚠️ 多版本累积成本高

### 3.2 多版本累积成本

#### 场景：10 次升级

| 方案 | 单次成本 | 10 次升级总成本 | 平均每次 |
|------|---------|---------------|----------|
| **EVM（新合约）** | 1,280,000 | 12,800,000 | 1,280,000 |
| **PVM（源代码替换）** | 640,000 + 5,000×9 | 685,000 | 68,500 |
| **混合（多版本）** | 1,280,000 | 12,800,000 | 1,280,000 |

**结论**：
- 🔴 **EVM 和混合方案**：多版本累积成本高
- ✅ **PVM 源代码替换**：多版本累积成本低（因为可以替换）

## 📊 第四部分：真实成本差异分析

### 4.1 我之前混淆的概念

#### 错误 1：把"迁移成本"误认为"存储成本"

**实际情况**：
- EVM 升级需要**部署新合约** → 用户需要**迁移** → 这是**迁移成本**，不是存储成本
- PVM 升级可以**原地升级** → 无需迁移 → **迁移成本为零**

**正确理解**：
- **存储成本**：链上存储数据的 Gas 成本
- **迁移成本**：用户从旧合约迁移到新合约的成本（时间、Gas、风险）

#### 错误 2：忽略了"多版本累积"的影响

**实际情况**：
- **单次存储**：字节码确实比源代码大 2-3 倍
- **多次升级**：EVM 需要多个合约，PVM 可以替换

### 4.2 正确的成本分析

#### 单次部署成本

| 方案 | 数据大小 | 存储成本 | 评估 |
|------|---------|---------|------|
| **EVM 字节码** | 2-3 KB | ~1,280,000 - 1,920,000 gas | ⚠️ 高 |
| **PVM 源代码** | 1 KB | ~640,000 gas | ✅ 低 |
| **PVM 字节码** | 2 KB | ~1,280,000 gas | ⚠️ 高 |

**结论**：**单次部署**，PVM 源代码确实成本更低。

#### 多次升级成本

| 方案 | 10 次升级总成本 | 评估 |
|------|---------------|------|
| **EVM（新合约）** | ~12,800,000 gas | 🔴 极高 |
| **PVM（源代码替换）** | ~685,000 gas | ✅ 极低 |
| **混合（多版本）** | ~12,800,000 gas | 🔴 极高 |

**结论**：**多次升级**，PVM 源代码替换成本显著更低。

## 🎯 第五部分：修正后的评估

### 5.1 存储成本重新评估

| 维度 | EVM | PVM（源代码） | PVM（字节码） | 混合方案 |
|------|-----|--------------|--------------|----------|
| **单次存储** | ⚠️ 高（2-3 KB） | ✅ 低（1 KB） | ⚠️ 高（2 KB） | ⚠️ 高（2 KB） |
| **升级成本** | 🔴 极高（新合约） | ✅ 极低（替换） | ⚠️ 高（新版本） | ⚠️ 高（新版本） |
| **多版本累积** | 🔴 极高（无法删除） | ✅ 低（可替换） | 🔴 极高（保留） | 🔴 极高（保留） |
| **迁移成本** | 🔴 高（需迁移） | ✅ 零（原地升级） | ✅ 零（原地升级） | ✅ 零（原地升级） |

### 5.2 综合成本评估

#### 场景 1：单次部署，不升级

| 方案 | 成本 | 评估 |
|------|------|------|
| **EVM** | ~1,280,000 gas | ⚠️ 高 |
| **PVM 源代码** | ~640,000 gas | ✅ 低 |
| **PVM 字节码** | ~1,280,000 gas | ⚠️ 高 |

#### 场景 2：多次升级（10 次）

| 方案 | 成本 | 评估 |
|------|------|------|
| **EVM** | ~12,800,000 gas | 🔴 极高 |
| **PVM 源代码** | ~685,000 gas | ✅ 极低 |
| **混合方案** | ~12,800,000 gas | 🔴 极高 |

### 5.3 修正后的结论

**我之前说"EVM 存储成本高"的原因**：

1. ✅ **单次存储确实高**（字节码比源代码大 2-3 倍）
2. ✅ **多版本累积成本高**（无法删除旧合约）
3. ❌ **但我混淆了"迁移成本"和"存储成本"**

**正确的理解**：

1. **单次存储成本**：
   - EVM 字节码：高（2-3 KB）
   - PVM 源代码：低（1 KB）
   - PVM 字节码：高（2 KB）

2. **升级成本**：
   - EVM：极高（需要新合约 + 迁移）
   - PVM 源代码：极低（可以替换）
   - 混合方案：高（需要新版本，但可保留旧版本）

3. **迁移成本**：
   - EVM：高（用户需要迁移）
   - PVM：零（原地升级）

## 🔚 第六部分：最终结论

### 6.1 存储成本的真实差异

**单次存储**：
- ✅ PVM 源代码确实比 EVM 字节码**便宜约 50%**
- ⚠️ 但差异不是数量级的（都在 KB 级别）

**多次升级**：
- ✅ PVM 源代码替换成本**显著更低**（可以替换，无需累积）
- 🔴 EVM 和混合方案成本**显著更高**（需要新合约/版本，无法删除）

### 6.2 我之前表述的问题

1. ❌ **过于简化**：只说"EVM 存储成本高"，没有区分单次和多版本
2. ❌ **混淆概念**：把"迁移成本"误认为是"存储成本"
3. ❌ **忽略场景**：没有考虑升级场景下的累积成本

### 6.3 正确的表述

**应该这样说**：

> **单次存储成本**：EVM 字节码比 PVM 源代码高约 2 倍（因为字节码包含更多元数据）。
> 
> **升级场景下的总成本**：EVM 需要部署新合约，累积成本高；PVM 可以替换源代码，累积成本低。
> 
> **迁移成本**：EVM 需要用户迁移，成本高；PVM 可以原地升级，成本为零。

### 6.4 对混合方案的影响

**混合方案（版本化字节码存储）**：

- ⚠️ **单次存储成本**：与 EVM 相近（字节码存储）
- ⚠️ **多版本累积成本**：高（需要保留多个版本）
- ✅ **但优势在于**：共识安全性 + 可升级性

**建议**：
- 如果**不需要多版本保留**，可以**删除旧版本**（类似 PVM 源代码替换）
- 如果**需要向后兼容**，可以**保留旧版本**（类似 EVM 多合约）
