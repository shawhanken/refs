02唯一的大未知:Swift 從沒編過

CI 從未在這個分支上跑過

workflow 觸發條件是 push: branches [main, devnet] 加 pull_request。 homestead-based-on-cip-39-v2 上有 0 次 workflow run、0 個 PR, 所以在 macos-26 runner 上的 app job(swift test --package-path apps/Homestead, 41 檔 / 17,130 行 / 561 個 test case)在 v2 上從未執行過。

PORT-PLAN 自己就寫著 “The Swift app is edited but unverified — there is no Swift toolchain on this machine”,而這台機器現在仍然沒有。已經改動、但一次都沒編譯過的檔案是:

  • RelayEndpoint.swift — 新 FFI 簽名、v2 綁定驗證
  • EditorWebView.swift — 整數 lane id、nativeGrantVerificationRequired
  • TrustedProtocolFloorStore.swift — configGeneration → authorizationGeneration 更名
  • CloudTrustBuild.swift — build-pinned provider root

偏樂觀的理由:FFI 已經綠了,代表 UniFFI 產生出來的 Swift binding 是自洽的, 剩下的多半是呼叫端的型別與命名層機械修正。偏保守的理由:沒編過就是沒編過。 這個數字要在第一次 swift build 之後才算得準——這也是為什麼上面的工期是「被第 1 步閘住」的。

好消息是這個分支有在維護:apps/Homestead 最後一次被改是 2026-09-02, 自 08-20 以來有 27 個 commit 落在 app 上。它不是被放著長灰塵的目錄。

05上線缺口:這才是真正的距離,而且不是寫碼

docs/homestead-v1-spec.md 的 completion sequence 有六步。第 1 步大致完成, 2–6 步基本沒動:

step 1 · 大致完成 整合 Homestead 與 CBFS 變更,重跑各 repo 的完整可行 gate
step 2 · 未開始 production KMS/CBFS role driver、committed chain transport、treasury funding、Stripe 設定、backup transport、監控重啟 wrapper —— 全部是外部憑證與帳號
step 3 · 未開始 dev 環境走完整條:card → committed hire → 兩個 volume → fresh relay receipt → writable actor,再走 lapse/recovery/revocation/export/backup/restore
step 4 · 未開始 對全量 workspace corpus 量 warm/cold open 與搜尋延遲,對照既定預算收斂回歸
step 5 · 未開始 OAuth 輪換、Developer ID 簽章、notarize、clean-install / 升級 / 更新 smoke
step 6 · 未開始 有營運告警、對帳、刪除保留、支援與匯出程序的限量付費外部 beta

發行管線本身已經寫好了

app → app-release(macos-26 上簽章 + notarize)→ publish(推到 updates bucket)三段都在 ci.yml 裡, 只是只在 main 上跑。版本號還停在 0.0.1。

順帶一提,spec 的 verification snapshot 停在 2026-08-03——那時 web editor 是 176 個測試, 現在是 675 個。那張表需要重寫。

06建議順序

這是一條真的依賴鏈:第 1 步之前,後面每一項的工期都是猜的。

  1. 先拿到 macOS 判決 對這個分支開一個 draft PR 讓 CI 跑 macos-26,或直接在一台 Mac 上 make build。
    ≈ 1 小時人力
  2. 修第 1 步吐出來的東西 編譯錯誤,加上 561 個 Swift 測試裡的紅字。
    1–3 天 / 悲觀 1–2 週
  3. 重建 bundle,讓 app 吃到 durability repair 幾分鐘的事,但這是會靜默吃掉使用者文字的 bug,價值最高。
    幾分鐘
  4. 補兩個功能洞 加入申請佇列、公開留言審核——服務端都已就緒。
    ~1.5 天
  5. app ↔ 現有 v2 devnet 端到端跑一次 broker 與 relay 都已經在跑。PORT-PLAN 說「沒有任何 live devnet e2e」——web 現在有了,app 還沒。
    1 天
  6. 才輪到 spec 的第 2–6 步 產品與營運工程,瓶頸在憑證、金流與外部帳號。
    4–8 週

!!要驗證的風險:信任錨與 devnet 重啟

devnet 一旦重新 genesis,所有已安裝的 .app 全部失效

app 的信任錨是 build 時燒進 Contents/Resources/trusted-checkpoint-v1.bin 的 217 bytes,TrustedCheckpointResource 明白寫著 “no actor or network fallback… fail closed”。

好消息:比對只看 chain_id 與 chain_instance_id,不看高度 ——所以錨點不會因為時間經過而過期,它是真正的 light-client 錨,往前的狀態靠 /cbqs/chain-proof 證明。

壞消息:chain_instance_id 綁的是這一條鏈的實例。 scripts/rotate-trusted-checkpoint.sh 只輪 relay 和 webeditor,沒有 app。 dogfood 期間要嘛固定 devnet instance,要嘛每次重建發版。
