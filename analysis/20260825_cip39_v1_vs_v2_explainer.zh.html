CBQS 规格 v1 → v2:全面对比与变更原由

这份文档写给没有读过 CIP-39、也不熟悉区块链或消息队列的读者。 每个术语第一次出现时都会解释,每个变更都会说明「原本怎样、现在怎样、为什么改、代价是什么」。

v1 4,827 行 v2 3,591 行 重置激活 · 无迁移 系统 actor 0x17

TL;DR一分钟导读

CBQS 是 Cowboy 链上的消息队列服务——让程序之间可靠地传递工作消息。 v2 是 v1 的完全取代版,砍掉了大约八成的机制。

所有变更几乎都是同一句话的推论:区块链不再参与每一次消息的传递。 v1 每处理一条消息都要读链、验签名、写收据;v2 只在「谁拥有这条队列、谁负责服务它、有没有付钱」这种 真正需要仲裁的事情上用链。

三个最大的数字

结构定义 80 → 16 个(协议里需要精确定义的数据格式数量)
每指令链上状态读取 233 → 48 次(运行一个链上操作要读多少笔数据)
签名对象 13 → 3 种(需要密码学签名的东西)

一个诚实的反例

行数只降 26%,而且中途一度上升(第一版草稿只有 1,390 行)。原因是:每一轮审查都在 删机制、加散文——补上「这条规则为什么存在」「它挡掉哪个分歧」「哪一版草稿写错了」。 那些散文正是后面几轮能分辨「承重的规则」和「装饰的规则」的依据。机制在减少,说明在增加。

①先搞清楚这是什么

什么是「消息队列」

想像一个餐厅的出单机。服务生把点单粘贴去,厨师一张一张撕下来做。点单机让两边不必同时在场: 服务生不用等厨师有空,厨师忙完再来拿下一张。

模拟:出单机

消息队列就是软件版的出单机。生产者(producer)把消息放进去,消费者(consumer) 取出来处理。这样两边可以独立扩容、独立故障、独立重启,而不会互相拖累。

CBQS 要解决的具体场景:Cowboy 上的 runner(运行 AI 任务、HTTP 请求的链下程序)之间 需要互相传工作消息,而这些消息不适合塞进区块链——太大、太频繁、太不值钱。

四个角色,分清楚就不会乱

Owner 拥有者在链上持有这条队列的人。他付钱,他决定谁能用。
Provider 服务商实际跑服务器、存数据、送消息的人。他收钱。
Broker 中介程序Provider 跑的那个服务器程序(cbqsd)。技术上做事的就是它。
Holder 凭证持有者拿到 owner 签发的授权、实际来读写消息的程序。
为什么要分这么细

因为付钱的人、做事的人、用的人可以是三批人。owner 可能是一家公司,provider 是它租的 服务商,holder 是它自己的十个微服务——每个微服务拿到的权限还可以不一样(有的只能写、有的只能读)。 规格必须说清楚每一条规则约束的是谁。

「链上」和「链下」差在哪

链上(on-chain)= 写进区块链的数据。全世界每个验证节点都要存一份、都要算出一模一样的结果。 好处是不可窜改、有公信力;坏处是又贵又慢。

链下(off-chain)= 普通服务器上的数据。快、便宜,但要信任跑它的人。

模拟:法院与仓库

链就像法院:适合登记「这间仓库是谁的」「租金付到几号」。你不会把每一箱货物进出都去法院公证一次—— 那既没必要,也瘫痪法院。

v1 的问题正是如此:它每搬一箱货都去法院盖章。v2 把法院的职责收回到 「谁拥有、谁服务、有没有付钱、谁被授权」这四件事上。

②术语表(下面看到不懂的词就回来查)

stream串流 / 队列

一条消息队列本身。CBQS 的基本单位,一个 owner 可以有很多条。

lane信道

串流内部的分类标签,像同一个出单机上分「凉菜/热炒/甜点」。不是独立队列——所有 lane 共享 同一个总顺序。

record / sequence记录 / 序号

一条消息叫 record。每条有一个严格递增的整数 sequence,从 0 开始,不跳号、不重用。

consumer group消费者群组

一组互相抢消息的消费者。同一条消息在一个 group 内只会交给其中一个成员处理,但不同 group 各自都会拿到一份。

lease租约

消息交给某个消费者时发的「暂时归你处理」凭证,有时限。超时没回报就收回重派——这样消费者当机 消息也不会卡死。

at-least-once至少一次

保证消息至少被送达一次,但可能重复。因为「刚好一次」在分布式系统里代价极高, 业界标准做法是至少一次 + 消费端自己去重。

idempotent幂等

同一个操作做两次和做一次结果一样。例如「把余额设成 100」是幂等的,「余额加 10」不是。 收到重复消息不出错的关键。

durable commit持久化提交

数据真的写进硬盘(而不是还在内存缓存里)。断电也不会丢。代价是慢——这是 v1/v2 的一个关键取舍点。

consensus state共识状态

链上所有节点必须完全一致的那份数据。每读一次、写一次都要计价,而且两个实现算出不同结果 = 分叉,是最严重的 bug。

governance parameter治理参数

可以通过链上治理投票调整的设置值(例如「一条串流最多几个 lane」)。v1 有 56 个,v2 剩 31 个。

grant授权凭证

owner 用链上密钥签发的一张「许可证」,写明持有者能做什么(读/写/管理)、能碰哪些 lane、有效到何时。

snapshot链状态快照

broker 定期从链上抓一份数据副本。v2 用它取代「每个请求都即时读链」。

Merkle proof默克尔证明

一种密码学技巧:能证明「某笔数据确实在一大堆数据里」,而不用把整堆都给对方看。v1 用它做 per-lane 证明,v2 拿掉了。

HPKE / 端到端加密

一套标准加密方法。v1 让平台帮用户管密钥和加解密;v2 不碰——应用自己加密好再丢进来。

CRDT无冲突拷贝数据类型

一种能让多人同时编辑、事后自动合并不冲突的数据结构(例如协作文档)。v1 的 fast 类别是为它设计的。

escrow托管余额

预先锁在链上、用来付租金的钱。v1 每条串流一份,v2 改成每个 (owner, provider) 关系一份。

backpressure背压

接收方告诉发送方「我来不及了,慢一点」的机制。没有它,慢的消费者会被塞爆。

dead-letter queue死信队列

处理失败太多次的消息被丢进去的地方。v2 把整套拿掉了(原因见第 ⑨ 节)。

conformance一致性(符合度)

一份「怎样才算正确实现了这个规格」的可测清单。v1 完全没有,v2 添加了一整章。

gas / metering计量

链上每个操作要收多少运算费。必须逐字节精确,因为两个节点算出不同的 gas 就是分叉。

③内核观念:链为什么不该在数据路径上

这一节值得单独讲,因为后面八成的变更都是它的推论。

图:v1 把链放在消息必经之路上(上),v2 把链移到旁边、只定期同步(下)。 这一个改动就决定了后面大部分的删除。
v1 的实际代价

每传一条消息,端到端要付:2 次客户端签名 + 2 次 broker 验签 + 2 次同步写硬盘 (一组给写入、一组给确认),外加一次链上共识状态读取。

更糟的是 v1 有个参数叫 cbqs.max_chain_staleness_blocks——链只要落后超过这个值, broker 就拒绝服务。也就是说链打喷嚏,整个消息队列跟着感冒。

v2 怎么做

broker 定期(默认 2 秒)抓一份链状态快照,一个请求就从一份快照判断到底。客户端开 session 时验一次签名,之后 session 内的请求都不带签名。

代价写在文档里:撤销授权不再是即时的。它被两个东西界定——正常情况是快照刷新间隔, 最坏情况是凭证本身的到期时间。规格明说这一点,而不是暗示更强的保证。

为什么「错误码几乎没少」反而是好事

更简单的协议不需要更少的失败名称,它需要更少的失败方式。后者是「结构定义」和 「状态读取」那两列在量的。

⑤变更一:链退出数据路径

1.1 授权方式:每请求验签 → 一次性 session

v1

每个请求(连读取都算)都带一个 RequestProofV1 签名,broker 对着即时读取的链状态验证。链太慢就整体停止服务。

v2

开 session 时验一次授权凭证,之后 session 内请求不带签名。 broker 用定期快照判断,链不可用时继续服务既有 session。

为什么

这同时是吞吐量天花板和可用性地板。而且撤销授权本来就不需要 即时读链——它需要的是「延迟有上界」,定期刷新就能给。

代价

撤销不再即时。上界:正常是快照刷新间隔,最坏是凭证到期。 规格明写。

1.2 收据:每条消息一张 → 每批一张

v1

每次写入返回一张 broker 签名的收据,串进全域和 每个 lane 两条哈希链。连 Ack/Nack/Extend/Reject/Redrive 和群组变更都各自有收据和自己的链—— 共 12 种带收据的动作。

v2

每个持久化批量一张 CheckpointReceiptV2, 用一个扁平摘要涵盖整批,再用连续性规则把批量串起来。消息路径上零非对称密码学。

为什么

批量提交(group commit)是所有主流消息中介达到高吞吐的办法。 而且更细的证据没有东西去消费它——v1 自己的信任模型就写明没有争议仲裁、没有质押、没有罚没。 证据再细也没有人能拿它去运行什么。

代价

证据粒度从「单条消息」降到「一个批量」。而且只持有批量 一部分的人根本无法验证——v2 把这句话明写出来,而不是让人误以为有逐则证明。

⑥变更二:计价从「按量」变「按条」

模拟:水表 vs 月租

v1 像装水表:按流量、按存量、按带宽三种单位分别计价,还分两种资费方案(标准/快速), 每种三个单位、每个单位两个参数——光资费表就 12 个 链上冻结参数。

v2 像收月租:一条串流每个区块固定多少钱,不管你传多少。

v1

一条签名报价路径 PriceQuoteV1 加上一套 管理式资费表(12 个冻结参数)。托管余额每条串流一份,有停权宽限期,租金还要扣掉链暂停的时间。

v2

一个 cbqs.stream_rate_per_block,从一个 按 (owner, provider) 记帐的预付帐户扣。没有报价、没有资费表、没有每串流托管、没有宽限期、 没有暂停时钟。

为什么

那些计量单位在计价「broker 本来就会用上限挡住」的容量—— 同一份风险被两套机制各挡一次。而两条资费路径意味着两套准入规则、两种失败模式、两组错误码,只为回答 同一个问题:这条串流这个区块可不可以存在?

代价

provider 无法对重负载的串流收更多钱。它的风险改由 §15 的每串流上限和它自己的 max_streams 界定,而不是靠价格。

− ActivateKeyGeneration− SetProviderStatus− SettleStreamRent − TopUpStream+ SettleAccount+ TopUpAccount + WithdrawAccount

设置值也离开了链

v1

StreamConfigV1:12 个字段的保留期、消息大小、 交付与加密设置,存成共识状态,改一次要送一笔链上交易。

v2

5 个 broker 端设置,每个在接受时对治理上限检查一次。 链上记录只剩 9 个字段,没有一个是设置、没有一个是钱。

为什么

这些东西不需要在两方之间仲裁——它是 owner 和它的 provider 之间的约定。放进共识只是让每次调参都变成一笔交易。链真正该仲裁的是:谁拥有、谁服务、 哪把密钥能授权、有没有付钱。

⑦变更三:四个子系统整个下架

这四个都是延后到后续 CIP,不是声明不需要。判断标准每次都一样: 这个机制检测或防止的东西,文档其余部分有能力处置吗?

3.1 fast 快速交付类别

v1 · 提到 109 次

第二种交付类别,有暂定确认、broker 世代、 FastLineageV1 血统追踪、Clean/Void 两种世代转换语意、暂定与持久两条水位线, 外加一整套规范性的 CRDT 重新同步进程。

v2 · 提到 1 次

只有一种交付类别。那 1 次出现在「被移除了什么」的清单里。

为什么

在还没有任何用户之前,一份文档里就放了两套持久性模型、 两条当机复原路径、两种识别码形状。

代价

这是真的退步,而且文档明说:协作光标、在线状态这类 workload 要多付一个批量窗口(约 20 毫秒)的延迟。这是最可能第一个被要求加回来的东西。

3.2 Lane 分区的 Merkle 证明

v1 · 约 400 行

两种树算法(含奇数节点提升规则和一段关于长度歧义 的论证)、固定深度 256 的稀疏树、bitmap 证明、规范化下降路径、每批量的每 lane 存在与不存在证明、 遗漏检测、两种验证模式。

v2 · 1 句话

每批量一个扁平摘要,外加一句「lane 范围的订阅者 无法验证 checkpoint」。

为什么

这套机制检测的是真实存在的缺陷(provider 偷偷漏送某个 lane 的消息)。但 v1 里没有任何东西能处置这个检测结果:没有争议机制、没有质押、没有罚没。 v1 自己对「provider 出问题」开的药方是「换一家」。检测得到但无法追究,等于没有。

代价

明说不藏:lane 范围的验证不可用,变通办法是「一个验证域 开一条串流」。要加回来,应该和让检测有意义的争议机制一起加。

3.3 平台加密、密钥串流、CBSS 托管

v1 · 加密 36 次 / CBSS 18 次

HPKE 信封、每条数据串流配一条密钥 串流、分块上传的密钥轮替批量(自带收据)、成员变更语意、一个专属链上指令 ActivateKeyGeneration、CBSS 门槛式根密钥托管,以及 5 个密钥批量参数。

v2

payload 就是不透明的字节。应用自己管密钥。 broker MUST NOT 解读 payload 内容。

为什么

把机密性做成平台服务,等于让协议负责密钥保管、轮替、 成员管理三件各自都有成熟独立解法的事,还把队列的发布时程绑在 CBSS 上。而应用自己先加密再丢进来, 拿到的保证更强——因为 broker 从头到尾连密钥都没碰过。

代价

原本想从平台拿到密钥管理的应用要自己做。§2 把 「payload 机密性」明列为非目标,免得有人误会。

3.4 签名的保留期锚点 + CBFS 归档

v1

三种签名锚点对象,外加把被淘汰的记录归档到 CBFS。

v2

一个「保留下限序号」,通过一个错误码的 payload 观测: CursorTooOld 带一个 u64。

为什么

锚点是「对一个你问一下就能知道的数字做签名声明」。 签它等于为了证明一件没有人在争议的事,多加一个对象、一条链、一条验证路径。

⑧变更四:五个「在补偿更下层选择」的机制

这五个有个共同形状:它们本身没错,但它们存在的唯一理由是补偿一个更底层的设计选择。 把那个选择改掉,它们就没事做了。

  • 端点验证离开共识。v1 在链上准入时跑一套五条规则的算法(禁用字节扫描、逐字节的 scheme 比对外加两段勘误、WHATWG URL 解析、私有网段检查)。v2 直接收下 URI 不解析,把地址检查交给 客户端——因为只有客户端知道它即将连到哪里。共识不可能知道一个主机名在连接当下解析到哪, 假装知道等于在状态机里开了一个 DNS 形状的洞。
  • Lane 不再背负协议机制。v1 把客户端选的 nonce 哈希成 lane id,于是需要:一个永久墓碑集合 (防止旧 id 被重建成不同历史)、一个对墓碑集合的上限、一个防止有人霸占命名空间的速率限制,以及当 两个上限同时满了会卡死的处理。v2 改成 broker 指派的单调递增整数,重用在构造上就不可能, 前三个直接消失。第四个(创建速率限制)留下来但换了范围——因为指派解决了「霸占」, 没解决「在固定月租下大量产生持久状态」的成本。
  • 一个指令一个事件。12 个事件变 8 个,每个成功指令一个,发布状态值而不是状态变化。 v2 明说后果(想知道某次结算是停权还是复权,自己 diff 前后区块的帐户状态),而不是宣称两者等价。
  • 应用指引离开规格。v1 的 Homestead 章节用规范性语气描述一种应用模式。 指引不是协议要求,一致性测试也测不了它。
  • 依赖从 8 个 CIP 降到 3 个。CIP-9(CBFS)、CIP-24(CBSS)、CIP-36,以及 CIP-2/CIP-10 作为 硬依赖,都随着对应的表面一起消失。

⑨变更五:v2 拿自己开刀砍掉的四个

前面所有变更都是「v2 对照 v1」。这一节不同——这四个是v2 的草稿写出来之后,经过对抗式审查 才被砍掉的。每一个都带着一个「修下去只会让文档变长」的缺陷。

5.1 broker 端去重

为什么

四版草稿试着给这个存放区设上界,每一版都生出下一个缺陷。 最后一版用「单调下限」,结果它拿客户端的时钟去比broker 的时钟——在完全合规的输入下 放进了一条重复消息,正是这个存放区存在要防的事。§9 把责任放回「至少一次交付」本来就要求的地方:消费端。

5.2 死信队列与 Redrive

为什么

草稿自己承认这个队列无法查看、只能盲抽。 那它就只是「盖在 log 已经按序号索引好的同一批字节上的第二个索引」,却自带 TTL、自带治理参数、 自带分页上限、自带一个和保留下限打架的回收期限,还有一个计数器——那个计数器存在的唯一理由, 是让被重驱的记录能排到后来的记录后面。

代价

只想拿失败消息的消费者,改成按序号重放 log,而不是抽一个队列。

5.3 StrictFifo 严格顺序模式

这是最值得看的一个

StrictFifo 模式只暴露「最低的未终结项目」。而保护共享群组的那个上限 max_in_flight_per_holder 最小值是 1——在 StrictFifo 下它等于没有保护。

后果:一个只拿到 CONSUME(最弱的消费权限,连终止都做不到)的持有者, 取走那唯一一个租约、然后什么都不做。租约超时十次,那条消息就走进终态。 然后换下一条。整个共享群组的每一条消息,都可以被一个「开了订阅之后一个字节都没再送」的人毁掉。

代价

想要顺序处理的群组,改用「一个排序域一条 lane」,而不是一个模式旗标。

5.4 Nack 的延迟参数

为什么

它让 §6.2 豁免于偿付能力检查的动作,能买到 §6.2 管制的动作的 120 倍生命期——直接推翻该节自己的判准。现在 Nack 在 「沉默超时本来就会释放的那一刻」释放,所以它不移动任何期限,而且主动回报永远不会比不吭声更糟。

⑩v2 添加的东西(简化不只是减法)

下面前三项,v1 完全没有对应章节。

  • 一致性章节(Conformance)。v1 没有。§19 说明「怎样才算正确实现」,并且另外列出哪些要求 是从外部观测不到的——这样读者能分辨「可稽核的保证」和「只能靠信任的义务」。
  • 激活章节(Activation)。v1 没有。§18 说明激活是重置、用封闭世界规则让 genesis 拒绝 所有 v1 参数(不必逐一枚举),并钉死保存格式标记键,让 v2 的 broker 打不开 v1 的数据库。
  • 钉住的 gas 矢量文件。27 条矢量涵盖每个链上指令的每个分支,用 SHA-256 钉在 §15.1 里, 逐条写明计费的读、写、cycles、cells。两个验证节点算出不同 gas 就是分叉,v1 把这件事留给散文。
  • 预付帐户对象与提领路径。钱从串流记录搬走之后,总得有地方放、有办法拿回来。
  • 运维面(§17)。定义 /readyz、/statusz、/metrics, 其中包含一条关键规则:链快照刷新失败 MUST NOT 让 broker 变成未就绪——这条规则才让 「数据面独立于链」在实务上成立(否则负载平衡器会把还能服务的 broker 全部摘掉)。
  • 新的 STREAM_ADMIN 权限比特,用 v1 留空的那一位,授权那些取代了链上设置的 §13 设置变更。

⑪刻意保留的,以及明说没关掉的

保留

  • 链控制的授权。用链上管理密钥签发、带世代计数器的凭证。没有它,CBQS 就只是一个 「自己维护客户名单的中间件」,而不是 Cowboy 的服务。
  • 带同意权的 provider 注册表。accepts_new 和 max_streams, 让一个无需许可的注册表不能把 provider 塞爆。
  • 至少一次语意,精简到工作队列真正需要的部分。租约、可见性超时、尝试次数、每持有者的 在途上限、四个租约动作。
  • 信用额度式背压(背压必须是明示的),以及先持久化再确认(否则就是静默丢失)。

明说没关掉的四个限制

为什么要写出来

因为藏起缺口的规格,比明说缺口的规格更危险。每一条都写在它实际会咬人的那一段旁边。

  • 没有 broker 身分认证。握手只认证客户端。网络位置攻击者(DNS/BGP 劫持、误发凭证) 事后可检测(provider 对每张 checkpoint 签名)但无法预防;链上帐户被攻陷的话, 攻击者一个指令就同时换掉端点和密钥,只能部分检测;两者都不能防「中继整个握手」,那需要这份文档 没有定义的信道绑定。
  • 两条速率上限有关联但不强制。扇出(一条消息要送给 N 个群组)意味着交付预算必须是写入预算的 某个倍数,§13 把不等式写出来但不验证。
  • 被拒绝的写入,其回应会放大流量。12 字节的请求配一个最大 2,093 字节的错误回应。 这是可以用计费规则关掉的,但没关。
  • 出向流量没有 per-holder 范围(入向有两层),而公平调度规则是 per-connection, 但连接数本身是运维问题不是协议问题。

⑫怎么激活:重置,不是迁移

为什么可以直接重置

CBQS 从来没有在一个「状态必须被保留」的网络上激活过,而且 v1 自己就把自己规定为 「仅限重置、发布前」。所以不需要迁移路径——这是一个难得的、可以干净切换的时机。

genesis 只种默认值种下注册表单例和每个参数的默认值,拒绝任何 v1 的参数键。
解码器认版本字节不是 2 的一律拒绝,链上 payload 和保存的记录都算。
保存格式标记v2 的 broker 打不开没有 v2 标记的数据库,不会做部分解码。
运维禁令不得把 v1 的链状态、broker 数据库或封存快照带过这条界线。

§18 特别用了封闭世界的写法:「genesis MUST 拒绝任何 §15 的表格没有列出的 cbqs.* 键」。这样就不必逐一列出 v1 的参数——一个验证节点不需要知道 v1 存过什么,就能拒绝它。枚举会过期,规则不会。
