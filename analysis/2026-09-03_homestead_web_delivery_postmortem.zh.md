## 1. 摘要

Homestead 的 Web 客户端完成了到 CIP-39 v2 的移植、在活的 devnet 上跑通、加上了工作区外壳、
放到公网名字后面，并从「不可用」做到「可用」。共 30 个 commit，
**26 个各自独立的缺陷，其中绝大多数是仓库里所有单元测试都能通过的**（§7 为索引）。

最后这个数字才是结论。这不是一个缺测试的项目 —— webeditor 有 596 个测试、collab-relay 有
210 个，而在几乎每一个上述故障发生时它们都是绿的。这些缺陷全都属于同一类：
**用与代码相同的理解写出来的测试，看不见它。**

在公网部署上首尾实测：

| | 之前 | 之后 |
|---|---|---|
| 一次载入 + 一次切页所传输的字节 | 43.75 MB | 0.29 MB |
| 冷启动，侧栏画出 | 从未（或 30 秒以上） | 1.1 秒 |
| 冷启动，页面可读 | 9.6 秒 | 2.9 秒 |
| 切换页面 | 12.6 秒 | 约 1.4 秒 |
| 新页面的文字到达另一个读者 | 永久停在一个字符 | 4–8 秒 |
| 一次正常开页的 console 错误数 | 3 | 0 |
| 谁能管理这个工作区 | 任何拿到网址的人 | 已登入的成员 |

第 3 节按**错误的形状**而不是按时间顺序来组织这些缺陷，因为形状会重复出现，时间顺序不会。

## 2. 阶段

1. **移植**（0902）。relay、共享 crate 与浏览器客户端按 v2 的线上格式重写：单一投递类别、
   broker 指派的整数 lane id、以 `RecordHeaderV2` 作为 AAD，以及由应用自己负责的 payload
   加密 —— 因为 v2 删掉了平台层加密。
2. **跑通**（0903 上半场）。链、provider、stream、TLS 后面的 broker、信任锚点、readiness
   仪式、ACL、relay、浏览器 —— 在一台机器上端到端跑通。
3. **外壳**。浏览器版此前只能打开**一个**由 query 参数指名的文档；页面树、权限与工作区只有
   macOS app 够得着。侧栏、分页、工具栏、搜索、分享与垃圾桶都是对着原生客户端所用的同一个
   Homestead actor 加上去的。
4. **公网单一 origin**。「回环 + 端口转发」经不起真实浏览器的检验。全部搬到一个已有真证书的
   nginx vhost 后面。
5. **性能**。每页 43.75 MB，外加一个十秒的停顿。
6. **交付**（0903 下半场）。最后一个正确性缺陷、安全姿态、运维硬期限、以及 console 噪音。

## 3. 缺陷，按形状分类

### 3.1 镜像实现的测试，看不见实现的错误

**`recordHeader` 把 lane id 写成了小端**，规范要求大端。封装与解开用的是同一个 helper，于是
每一条往返测试都在自我印证，而它写出去的每一条记录对**任何其它方**都不可读。测试助手镜像了
实现，所以它永远不可能抓到这个错。

**如何解决。** 不是靠再写同类测试 —— 而是取一条来自 **Rust codec** 的向量，那是契约的另一端。
一般规则：**编码是两方之间的契约，只问其中一方的测试等于什么都没测。**

同一形状还出现了两次：

- **快照 head 的签名三方不一致。** 生产端对 signing bytes 的 `keccak256` 签名（这是 CBQS 的
  通用约定，`verify_cbqs_signing_bytes_strict_v2` 内部就这么做）；共享 crate 里手写的
  `sign_head`/`verify_head` 却对原始字节签名；而**冻结的跨语言向量正是由后者生成的**。
  于是向量与 TypeScript 完美互证，而 relay 发布出去的东西没有任何读者能验。
  **两个签名调用点就是这种问题的温床**，最后收敛成一个。
- **nonce 绑定了写入时不可知的量。** `payload_crypto` 用 `(lane_id, sequence)` 派生 nonce，
  但 `AppendRequestV2` 是 `{lane_id, payload}` —— sequence 只在 `Appended{sequence}` 里返回。
  写入方只能用本地计数器顶替，于是读取方用真 sequence 永远解不开，而 AEAD 失败看起来
  跟数据损坏一模一样。改为帧内随机 nonce + XChaCha20-Poly1305（192 位，随机 nonce 安全）。

### 3.2 删掉某个专用机制 ≠ 删掉那个能力

早期写进移植计划的一条结论 ——「v2 删掉了链证明，所以只能信任节点」—— 是**错的**，而且它会让
产品失去自己的信任模型。v2 只删掉了 CBQS 专用的 `CbqsChainProofBundleV1`。通用的
`FinalizedStateProofBundleV1` 还在，节点仍然提供 `POST /proof/finalized-state`，
`cowboy-protocol-light-client` 仍然负责验证。CBQS 的 stream record 本身就是 Stream Registry
（`0x17`）下的普通 actor storage。

**提炼出的规则**：在断定某个能力消失之前，先去找那个取代了专用机制的通用机制。

镜像的错误也同时存在：**relay 调用了 5 个 v2 节点根本不提供的端点**
（`GET /cbqs/broker-state` ×4、`GET /cbqs/chain-proof` ×1）。它的测试之所以是绿的，是因为
假节点照着 v1 的形状实现了它们。**判断一个客户端是否可用，要去被调用方的路由表里核对**，
而不是看调用方自己的测试。

### 3.3 按协议设计就是静默的失败

这类最费时间，因为根本没有东西可读。

- **浏览器拒绝 WebSocket 的证书是静默的。** 没有中间警告页，因为没有导航；而无论是证书被拒、
  主机不在、还是端口从未转发，关闭码都是 1006。产品里每一页都显示「Couldn't connect to this
  page —— 请从侧栏重新打开」，而「重新打开」恰恰是唯一永远不可能有用的补救。仓库里每一个
  harness 都带 `--ignore-certificate-errors` 运行，而这正是真实浏览器**永远不会有**的条件 ——
  于是所有检查全绿，而对所有人都不能用。
  **解法**分三步：一个 `no-cors` fetch —— 它**确实**能区分「连不上」与「连上了但被拒」；
  一个没有 bundle、没有依赖的 `/diagnose` 页面，在当事人自己的浏览器里跑检查并打印可复制的
  纯文本；最后是把问题本身消掉 —— broker 的 socket 搬到已有真证书的 vhost 后面，于是
  不再存在第二张可被拒绝的证书。
- **§11.2 的信用：订阅开场时信用为零，此后 broker 静默地什么都不投递**，因为「没有信用就不
  投递」正是协议在正常工作。一个开了订阅却忘了授信的 snapshotter，和一个流本来就空闲的
  snapshotter，从外面看完全一样。
- **`At(0)` 不指向任何记录。** §9.1 的 erratum 把记录起点移到 1，并保留 0 作为「不含」下界，
  于是从起点重放时问 `At(0)` 会被拒。checkpoint 的 `first_sequence` 也不是答案 —— 它只界定
  一个批次，从那里开始会**静默跳过**在它之前提交的全部记录。客户端学到真实 floor 的唯一途径
  是 §12 的 `CursorTooOld`，它把 floor 带在身上。
- **已经出队却被丢掉的帧。** `flushOutbound` 从会话队列里取走一帧，然后在 socket 未打开时把它
  丢掉。会话认为自己已经发出了这条记录；唯一的副本没了；没有任何东西报告任何事。

### 3.4 被测量的东西不是真正花时间的东西

公网部署之前的每一次计时都是**在服务器上**取的，而在那里 10 MB 只有 110 毫秒。从浏览器看，
一次载入加一次切页移动了 **43.75 MB**：

- 其中 41 MB 是 CBQS 链证明，被取了**四次** —— 每个 channel 一次、每页一次。它本是每个
  `(stream, checkpoint height)` 对应一个不可变 bundle，URL 里两者都写明了，但每次 fetch 一
  settle 就被丢弃；那个 in-flight map 只合并**并发**的 fetch。
- 另外 2.4 MB 是 bundle 自己的 HTML 被当作字体下载然后扔掉。一条 catch-all 路由用 bundle 回答
  所有未知路径，而 `/fonts/*` 在 macOS WebView 里能在 app bundle 内解析、在这台服务器上解析
  不到。

光是把 bundle 留住还不够：**那次 fetch 同时也是一个被撤权的读者得知自己被撤权的地方**，
跳过它会把拒绝转移到另一个阶段。修法是**保留请求、去掉字节** —— 用 `If-None-Match`，
relay 回 304。单靠 HTTP 缓存不可靠：RFC 9111 §3.5 规定，携带 `Authorization` 的请求，其响应
若无 `must-revalidate` 便不得存储；而 Chrome 无论如何也不愿意存 10 MB，这是它的权利。

还有一个**九点九秒、其间什么都没发生**的空档，最后查出是
`verifyPrunedOriginFallbackReadiness`：bootstrap 等它，并把结果赋给一个**被赋值两次、
从未被读取**的变量。这道闸要的是一个原生 body，而没有任何浏览器宿主会提供，
所以在浏览器里它只可能落到自己的 10 秒超时，然后把 `false` 答进一个没人看的地方。
去掉的是那个 `await`，闸本身原样保留 —— 把它接到消费端是另一回事。

### 3.5 是悬崖，不是斜坡

这个系统里有三处上限不会退化，它们直接停住。

- **页面注册表。** `api/pages/list` 会加载整个注册表，超过约 60 页就会超出 actor 的单次
  cycle 上限。gateway 把它变成 502，于是**整个工作区根本打不开** —— 包括 `api/delete`，
  也就是唯一能让它变小的那个调用。gateway 的上限已经在 39M，接近区块上限，旋钮用尽；
  而把 gateway 上限设到**高于**区块上限则会让所有**写**被拒、读却照常，看起来完全不像
  一个上限问题。**解法**在客户端：这条路由一直带着 `limit`/`cursor`，只是没人用。
- **snapshotter 的连线。** §11.2 要求每条 lane 一个订阅，而这个 broker 每连线只准 256 个，
  于是 130 页出头就越过天花板 —— 而且它不会退化，它在订阅**任何东西之前**就返回，于是
  没有任何 lane 被物化、没有任何 generation 被发布，此后创建的每一页读回来都是空的。
  **lane 从不回收**：通过 actor 删掉 63 页之后，注册表里 262 条 lane 一条不少。目前只以一条
  「说清代价」的消息缓解；真正的修法（跨多条连线）尚未做。
- **信任锚点。** 见 §3.7。

注册表这道悬崖是**真的撞上了**，而且**是被测试而不是被人撞上的**：`converge.mjs` 与
`check-shell-e2e.mjs` 每跑一次就留下一页，工作区 71 页里有 64 页是测试垃圾。其中一个 harness
本来就有「清理」—— 但它用的是**丢进垃圾桶**，而被丢的页面仍留在注册表里、成本一分不少。
现在两个都改成真删除。

### 3.6 耗时最久的那个缺陷：发布把自己的尾巴留在原地

**症状。** 一个被创建、被打字、然后由一个与写入方不共享任何存储的浏览器打开的页面，大约
一半的机率显示不出文字。最极端的形态是 relay 的副本里只有**一个字符**，并且就停在那里 ——
重启 relay 不变、整表重建索引不变、等多久都不变。

这件事追了四次，其中三次改完更糟。如实记录：

1. *让每条 lane 从自己的 cursor anchor 开始。* 这是 cursor 的结构本身所主张的做法。但把一条
   **没有 anchor** 的 lane 送去起点，会重建出一个比它已发布的 head 更旧的副本，而 store 会
   拒绝 —— 于是「一半的时候失败」变成了**每次都失败**。
2. *把被拒的发布当成非致命。* 它失败的原因值得记住：**是重连清除了那个拒绝**，因为新会话会
   验证 broker 接下来给出的任意 checkpoint，而一个被保活的会话会永远重复提供同一个。
3. *客户端侧的补救* —— 读者若发现打开的页面比 relay 所说的更空，就改为从起点重放而不是水合。
   这是对的，而且对已经存在至少一个 snapshotter 周期的页面有效。它救不了最新的页面，因为
   relay 的回答来自与快照同一份索引，陈旧程度完全一样。它的第一版还读了
   `surface.textContent` —— 而加载遮罩自己的文案就是 surface 里的文字，于是它永远看不到空
   页面，**测试全过、在应用里什么都没做**。
4. *把补救的窗口* 从 4 秒放宽到超过一个发布间隔 —— 因为实测发现一个新页面在被打字之后约 8 秒
   才到达 relay 的副本。4 秒的检查**根本不可能**抓到任何一个。

**真正的原因**，是靠给写入路径加追踪、再顺着记录往下游追出来的：一个已发布的 generation
绑定它所依据的 checkpoint position，而**一个 position 只承载其中一个**。同一个 position 上的
第二次发布会被跳过 —— 而且是**永远**跳过，因为 checkpoint 只在有新记录提交时才前进，而
一个没人再打字的文档不会提交任何东西。v2 是**靠问来确立覆盖**的，所以一个 checkpoint 的记录
是以一连串「每次一条投递」的方式到达的，而计时器驱动的发布就插在其中一次的中间。那次发布
之后才被应用的一切，永久发不出去。更早被打字的页面之所以看起来正常，只是因为后来**无关的
流量**推进了 position 顺手把它们带了出去 —— 这正是它一直表现得像「时好时坏」而不是像一条
规则的原因。

**修法是一个条件**（`may_publish`）：**取到帧的那一趟不准发布**。唤醒计时器保证活性 ——
无论流以后是否还说话，一个脏副本都会在一个发布间隔内等到一趟安静的循环。

**这个诊断实际需要什么**，按顺序，因为每一步都有一个现成的错误答案：

- 客户端里一个按需开启的逐次 append 追踪（`?cbqstrace=1`），它显示 42 次 append 全部被接受、
  全部成帧 —— 从而洗清写入方；
- 一份**按 lane 分组**的 append 直方图 —— 因为最前面六条全是前一个已打开页面的 awareness
  流量，只看那几条会得出「文档通道根本没被调用」的结论；
- relay 自己的日志，它显示 24 个 checkpoint-covered batch 到达，然后是**整整四分钟一行都没有**
  —— 那是一个「已经停住」的组件的形状，不是「正在出错」的形状；
- 去读**更早**那些房间的内容，它们已经完整收敛。正是这一步把「记录在丢失」变成了
  「发布在被跳过」，而它只是一条 `curl`。

追查途中还发现并修掉了两个**真实但不是本因**的缺陷 —— 重复打开导致 `Y.Doc` 被丢弃，以及
`flushOutbound` 丢帧。两个都是真的；两个都没有改变症状。追查中途写下的一句把症状归因于
`flushOutbound` 的注释，在提交前已被更正。

### 3.7 一个伪装成常量的运维期限

浏览器所验证的 finalized-state 证明，携带**从锚点到被证明高度之间的每一个区块头** ——
`fetch_history` 一个一个地走。所以它的体积不是「被证明的内容」的属性，而是「锚点有多旧」的
属性：本处实测为**每区块 228 字节**，链速每秒一块。

| 锚点年龄 | 证明体积 |
|---|---|
| 1 小时 | 0.8 MB |
| 1 天 | 18.8 MB |
| 3.4 天 | 64 MB —— `MAX_FINALIZED_STATE_PROOF_BUNDLE_BYTES_V1` |

越过这个界限，节点**根本产不出证明**，所有客户端停摆。而远在它之前部署就已经不可用：锚点
落后 14 小时就让每次证明达到 8.6 MB，侧栏从 2 秒变成 30 秒以上。**这不是 devnet 的特有问题**
—— 任何 CIP-39 v2 部署都在构建期钉住一个锚点，其客户端都要为「与锚点的距离」付费。

**解法**是 `homestead/scripts/rotate-trusted-checkpoint.sh`：按 lag 自我节流，所以可以安全地
每小时从 cron 跑；`--check` 只报告不动作；任何一步失败都停下，并保持旧锚点仍在位、relay 仍在
运行。其中两件不显然、且都是吃过亏才知道的事：

- **铸锚点前必须停掉 relay。** 节点对 `/proof/finalized-state` 限流，而 relay 是它最大的
  客户端，否则铸造工具会以「stayed rate-limited across every retry」放弃。
- **用 `pgrep -x` 按进程名定位 relay。** 一个 `-f` 模式若写着二进制名，也会匹配到**承载这条
  命令的那个 shell 本身**，于是 `pkill -f` 会把调用者一起杀掉。

一次轮换是**五件事**（重铸、重编 relay —— 锚点是构建期的、重生成 `shell-config.json`、
重打 bundle、重启），少做任何一件都会让旧锚点继续生效**且不报任何错**。漏掉第三件的结果是
证明体积纹丝不动。

### 3.8 部署姿态

`serve-demo.mjs` 在每次页面载入时铸造一个**工作区管理员**令牌并注入。这在它只监听回环时是对的；
放到公网名字后面之后，它意味着**任何能打开这个网址的人都是管理员** —— 能读所有页面、能编辑、
能加成员。

登入功能**写好了但不可达**：没有任何地方把 client id 放进 `shell-config.json`，于是
`googleAvailable` 在所有部署上都是 false，面板显示「本部署未设定登入」。还有两个缺陷让它看
起来像「配错了」而不是「还没就绪」：GIS 脚本是在面板画完**之后**才到达的，而没有任何东西重绘；
以及「没有 client id」与「脚本还没到」被报成同一件事，而两者中只有一件是运维的责任。

现在：注入改为选择性开启（`?demo=1`，供无法完成 Google 登入的 harness 使用），裸编辑器保留
注入（它根本没有登入 UI），而访客为自己登入。

### 3.9 淹没信号的噪音

每次开页都产生两条 console 错误 —— 来自取 comments lane 的 proof bundle，而它 404，因为从来
没人留过言：一个**正常状态被报成错误**。每次切页还多一条：CBQS driver 对**任何** socket 关闭
都 `console.error`，包括它自己刚刚请求的那一次；而握手尚未完成时的关闭报 1006 ——
在 console 里与「broker 完全联系不上」无法区分。`fatal()` 一直都会忽略这些；只有那行日志不会。

现在：未发布的 lane 回 **204**；我方主动请求的关闭不再记录。`check-shell` 对公网部署运行的
结果是 **console 零 problem**。

---

## 4. 难点在哪里

五种重复出现的形状，大致按各自消耗的时间排序。

1. **故障没有错误信息。** 或按协议静默（零信用、1006），或按惯例静默（空文档本来就是合法
   文档），或因为那个值被赋值而从未被读取。**大部分时间花在「造出一个可观测量」上，而不是
   花在修上。**
2. **测试与代码共享了同一个假设。** helper 里镜像的编码；按调用方预期造出来的假节点；
   由错误的签名者生成的 fixture；被预先塞好内容的 volume 让待测的 fallback 根本走不到；
   被钉住的 helper 而它的调用点自由。以上每一次，测试都是绿的、产品都是坏的。
3. **复现环境本身不具代表性。** harness 带 `--ignore-certificate-errors` 跑；计时在服务器上
   取；而那个测试工作区的 harness 同时也是把工作区塞满的东西。
   **在错误位置取得的测量比没有测量更糟，因为它会被相信。**
4. **「时好时坏」底下有一条规则。**「大约一半失败」最终是确定性的：发布落在批次中间，而一页
   看起来是否正确，取决于**后来无关的流量**是否恰好把它带出去。追统计而不追机制，产出了三个
   越改越糟的修法。
5. **这些上限是悬崖。** 工作区在 60 页时不是变慢，而是停住；snapshotter 越过天花板不是少发布
   几条 lane，而是一条都不发布。任何「只增不回收」的东西 —— 页面、lane、锚点与链头的距离 ——
   都是一次**已排好期的故障**，而不是一个性能问题。

## 5. 方法笔记

把有效的做法写成实践，而不是叙事：

- **用另一个实现来钉编码**，绝不用自己的镜像。
- **去被调用方的路由表里问**这个客户端能不能用。
- **变异要打调用点，不是 helper。** 围绕 `may_publish` 的三条单元测试，在调用点被改成传
  `true` 时**依然全绿**：它们钉住了谓词、别的什么都没钉；「调用点确实起作用」这件事的证据是
  devnet A/B，运行手册里写明了这一点。同样的形状此前出现在 `published_body` 上 —— 钉住
  helper 让调用点自由。
- **几何断言要在真引擎里验。** jsdom 不建模「自定 `display` 压过 `[hidden] { display: none }`」
  —— 把守卫删掉断言照过，把守卫反过来断言也照过。改为在真浏览器里量
  `getBoundingClientRect`。
- **改完更糟就说出来并回退。** §3.6 的四次尝试就是如此，其中三次记录在运行手册里而不是代码
  里 —— 而第五次尝试的信息正是从那里来的。
- **去读同一件事更早的实例。** 相隔一小时被打字的两个房间，一个完整一个冻结，这就是 §3.6
  的全部诊断。
- **一个变安静的组件是停住了，不是变慢了。** 四分钟没有日志，比任何错误信息都更强的信号。

## 6. 现状

**可用**：需登入、工作区树、开页、编辑、跨浏览器 4–8 秒收敛、搜索、分享链接、垃圾桶、
单一公网 origin + 真证书、锚点自动轮换、console 无错误。测试套件全绿 —— webeditor 596、
collab-relay 210。

**未完成**，按咬人的力度排序：

1. **snapshotter 只有一条连线**，所以约 128 页是硬顶，越过之后整个工作区停止收敛 ——
   比它取代的那个 502 更糟。需要改成跨多条连线。
2. **删页时 lane 不回收**，所以逼近那个天花板的计数只增不减。
3. **actor 每次 `pages/list` 仍然对全部页面做 O(n) 的 ACL 扫描。** 客户端分页移动了悬崖的
   位置，没有移除它。
4. **UI**：移动/排序、图标选择、垃圾桶视图、工作区切换、留言入口、快捷键、移动版侧栏、
   可调宽侧栏。
