# CIP-25 §2.6 Amendment Proposal — Cross-chain streaming (`send_stream`) soundness

**Status:** DRAFT proposal for team/governance review. Amends `cowboy/docs/cips/cip-25-cross-chain-architecture.md` (authoritative; verified against `origin/main` @ `5803cb2`). **Spec-layer change → highest review tier.** Presented as a proposal — the open governance choices (esp. C) are flagged, not decided.

**Motivation.** A 3-lens adversarial deep review of the COW-1901 implementation plan (which builds `send_stream`/`deliver_stream`) found the §2.6 "Cross-sender total ordering" row **under-specified in three load-bearing ways**. As written, a faithful implementation is (1) ambiguously keyed, (2) forgeable, and (3) permanently haltable by anyone. This amendment resolves all three so the primitive is implementable and sound. COW-1901's implementation is **blocked on landing A + C** (B is strongly recommended).

Primary-source anchors (line numbers in the CIP-25 file at `5803cb2`):
- §2.5 note (L291), §2.6 "Cross-sender total ordering" row (L301), glossary `send_stream` (L997).
- Conflicting `stream_id` formulas: §2.6(3)/glossary = `keccak256(dst_chain ‖ recipient ‖ topic)`; §3.3 (L377) + A.3 (L570) = `keccak256("oracle:" ‖ feed_id)`; §2.6(6) = "Watchtower stream hash".
- §2.6 "Timeout / cancellation" row (L293-…), §1.6 "Stale commitment consumed" + revocation (L205-206), threat-model "Cross-sender ordering race" (L885-area).

## A. `stream_id` derivation is normative and destination-computed (resolves B2)

**Problem.** Three mutually-inconsistent `stream_id` formulas appear in the spec. If a destination trusts a *sender-supplied* `stream_id` (as the raw value), a caller can pass a `stream_id` unrelated to `(dst_chain, recipient)` and interleave/hijack another recipient's stream (the per-stream counter is namespaced by that value at both ends). "Globally unique" (L301(3)) is a *namespacing* claim; it is not *authorization* and it is not *self-verifying* unless the destination recomputes it.

**Resolution (normative):**
1. `stream_id ≡ keccak256(dst_chain ‖ recipient ‖ topic)` is the **single normative definition** (§2.6(3), glossary L997 win; the §3.3/A.3 and Watchtower forms are reconciled below as *topic* choices).
2. The wire header commits **`topic`** (a 32-byte application-chosen tag), **not** the raw `stream_id`. Both `send_stream` (source) and `deliver_stream` (destination) **derive** `stream_id` from the message's *authenticated* header fields `dst_chain`, `recipient`, and the committed `topic`. A sender-supplied `stream_id` MUST NOT be trusted; destinations that store a raw `stream_id` are non-conforming.
3. Reconcile the examples as *topic* values, not whole `stream_id`s:
   - Oracle (§3.3 L377, A.3 L570): `topic = keccak256("oracle:" ‖ feed_id)` (or `topic = "oracle:" ‖ feed_id`), hence `stream_id = keccak256(dst_chain ‖ consumer ‖ topic)`. The bare `keccak256("oracle:" ‖ feed_id)` form is **removed** (it omits `dst_chain`/`recipient`, so two different consumers could collide on one stream and one consumer's rounds could be delivered to another).
   - Watchtower egress (§2.6(6)): `topic = Watchtower stream hash`; `stream_id = keccak256(dst_chain ‖ recipient ‖ topic)`.

**Text edits:** rewrite §2.6(3); fix §3.3 L377 and A.3 L570 to derive `topic` then `stream_id`; align glossary L997.

## B. Producer authorization — `open` vs `bound` streams (resolves the deep review's forged-round HIGH)

**Problem.** §2.6(1) says "**any sender** calling `send_stream` increments the per-stream counter", and `stream_id` inputs are all public (derivable). So under a known `stream_id`, **any actor can inject a genuinely-attested message** that `deliver_stream` accepts (it checks only `seq`). A consumer that infers "delivered on stream S ⇒ produced by the oracle" (exactly the §2.5/§3.3 oracle/inference use case) therefore consumes **attacker-forged rounds**. The spec conflates "unique namespace" with "authorized producer".

**Resolution (normative):** a stream is one of two modes, fixed at open time:
- **`open`** (the current §2.6(1) model): any sender may append; the primitive provides **total ordering only**. Consumers of open streams **MUST NOT** infer producer identity from stream membership.
- **`bound`**: the stream is opened with a registered publisher set `publishers[stream_id]`. `send_stream` reverts unless the **authenticated** caller (`rt.get_sender()` on Cowboy; `msg.sender` semantics on EVM — never a payload field) ∈ `publishers[stream_id]`; `deliver_stream` additionally `require(header.sender ∈ publishers[stream_id])`. Producer authenticity is then guaranteed end-to-end.

Oracle, inference, and any stream whose consumer trusts the producer (§2.5, §3.3) **MUST be `bound`**. This preserves §2.6's multi-sender capability (open streams) while giving the trust-sensitive cases a sound model, and it aligns with §2.5's single-logical-producer `StreamActor`. (Authentication builds on the CIP-25 bridge hardening that binds cross-chain sender identity to the authenticated caller, not a spoofable `_sender` — node PRs #1159/#1161.)

**Text edit:** add "(4a) Stream modes" to the §2.6 row; annotate §3.3/A.3 oracle streams as `bound`; add a threat-model row "Forged stream round" → mitigation "bound-stream publisher binding".

## C. Liveness: contiguity vs. terminal delivery-gates — the gap protocol (resolves B1) — **governance choice**

**Problem.** `deliver_stream` enforces `seq == expected_next_seq[stream_id]` and advances **only on successful delivery** (L301(2)). But every terminal reject-gate the spec already defines for a message makes a specific `seq=k` **permanently undeliverable**, which wedges the entire stream (head-of-line deadlock for all `k+1, k+2, …`):
- **Expiry hard cutoff** — §2.6 "Timeout/cancellation" (2): `Mailbox_E.deliver` reverts once `block.timestamp > msg.expiry`. One relayer stall past `expiry` on one seq halts the feed forever.
- **Revocation** — §1.6(3): a `commitment_revoked(chain, height)` message makes that height non-deliverable by design.
- **Proof-TTL ceiling** — §1.6 "Stale commitment": a commitment aged past the ceiling is rejected forever.
- (Impl note, not spec: the reference `FraudWindow._verifyFraudEvidence` is a demo stub accepting any non-empty evidence — deferred to ζ-4 — so today *anyone* can poison a block and amplify one poisoned slot into a whole-stream halt. Even with a real verifier, a legitimate source reorg triggers the same via revocation.)

The existing §2.6 "Timeout" flow recovers the **sender's escrow** but **does not advance the destination counter** — it does nothing for stream liveness. Total ordering and liveness are in direct conflict and the spec resolves neither.

**Resolution (proposed — governance decision required):** add a destination gap-recovery primitive.
- **`skip_stream(stream_id, seq, gap_proof)`**: advances `expected_next_seq[stream_id]` past `seq` **only** on a `gap_proof` that `seq` is permanently undeliverable, and emits `StreamGap(stream_id, seq, reason)`. Valid `gap_proof` (reusing existing machinery, no new trust):
  1. **Expired-and-undelivered** — `now > expiry + GRACE` **and** a reverse L1 commitment shows no `Delivered(msg_hash)`/`StreamDelivered` on destination for that `(stream_id, seq)` (the same reverse-commitment the Timeout row (4) already relies on).
  2. **Revoked** — the commitment carrying `seq` is in the §1.6(3) revocation set.
  3. **Aged-out** — the commitment is past the §1.6 proof-TTL ceiling.
- **Consumers observe `StreamGap`** and apply their own semantics: an oracle treats seq=k as a **skipped round** (safe — it already rejects `round_id ≤ last`, §3.3 L379); a value-transfer stream treats it as an alert/reconcile point. The gap is **explicit and proven**, never a silent skip.
- Streams SHOULD set `expiry` per the §2.6(6) recommended values; the stream author thereby accepts that an undelivered seq becomes an *acknowledged gap*, not a stall.

**Open governance question (for the team):** is an *acknowledged, proven* gap acceptable for the streaming guarantee (recommended — the only alternative to permanent halt), and should `skip_stream` be permissionless (anyone with a valid `gap_proof`) or restricted? Recommendation: **permissionless with mandatory proof** — liveness is a public good and the proof is self-validating.

**Text edit:** add "(2a) Contiguity with proven gaps" + the `skip_stream`/`StreamGap` definition to the §2.6 row; glossary entry for `skip_stream`; threat-model row "Stream halt (undeliverable seq wedges feed)" → mitigation "proven-gap `skip_stream`".

## Proposed §2.6 row — replacement text (drop-in)

> **Cross-sender total ordering** … | StreamID primitive + producer modes + proven-gap recovery + serializer-chain delegation:
> **(1) Primitive `send_stream(topic, payload, gas_limit) → seq`**: `stream_id = keccak256(dst_chain ‖ recipient ‖ topic)` is derived from authenticated header fields (the header commits `topic`, never a raw `stream_id`); source Mailbox maintains `next_stream_seq[stream_id]` atomically and writes `seq` into the message.
> **(2) Destination contiguity**: `deliver_stream(msg, proof)` accepts only `msg.seq == expected_next_seq[stream_id]` (out-of-order reverts); on success it increments and dispatches. **(2a) Proven gaps**: `skip_stream(stream_id, seq, gap_proof)` advances the counter past a provably-undeliverable `seq` (expired-and-undelivered via reverse commitment / revoked per §1.6(3) / aged past the proof-TTL ceiling) and emits `StreamGap(stream_id, seq, reason)`; consumers handle the acknowledged gap per their semantics.
> **(3) `stream_id`**: `keccak256(dst_chain ‖ recipient ‖ topic)`, destination-recomputed, globally unique. Sender-supplied `stream_id`s are never trusted.
> **(4) Single-source case**: works directly — Cowboy deterministic execution gives atomic seq assignment. **(4a) Modes** (fixed at open time, not per-send): a stream is `bound` iff `register_stream(topic, publishers)` was called for it (then `send_stream`/`deliver_stream` enforce authenticated `sender ∈ publishers[stream_id]`), else `open` (any sender; total-order only; consumers MUST NOT infer producer identity). Trust-sensitive streams (oracle/inference, §2.5/§3.3) MUST be `bound`. A sender cannot change a stream's mode mid-stream.
> **(5) Multi-source case**: L3 serializer-chain delegation (unchanged).
> **(6) Watchtower alignment**: `topic = Watchtower stream hash`; each Watchtower message auto-triggers a `send_stream`.

## Impact / rollout
- **No L1 change** (streams carry standard commitments; L1 anchors `receipt_root` regardless). Consistent with §2.5 "L1 requires no additional work".
- **New cross-repo wire** (the `topic`-carrying stream header + `mailbox.stream.v1` event + `StreamGap`): once shipped it is a frozen contract, same discipline as the 320-byte header.
- **Consequential doc edits** listed under A/B/C above (§2.5 note, §2.6 row, glossary L997, §3.3 L377, A.3 L570, three threat-model rows).
- **Unblocks COW-1901** (example `send_stream`/`deliver_stream` + oracle stream demo). A/C are hard blockers; B is required for the oracle example's correctness.
