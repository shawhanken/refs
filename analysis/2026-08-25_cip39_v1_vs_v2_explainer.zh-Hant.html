CBQS 規格 v1 → v2:全面對比與變更原由

TL;DR一分鐘導讀

CBQS 是 Cowboy 鏈上的訊息佇列服務——讓程式之間可靠地傳遞工作訊息。 v2 是 v1 的完全取代版,砍掉了大約八成的機制。

所有變更幾乎都是同一句話的推論:區塊鏈不再參與每一次訊息的傳遞。 v1 每處理一則訊息都要讀鏈、驗簽名、寫收據;v2 只在「誰擁有這條佇列、誰負責服務它、有沒有付錢」這種 真正需要仲裁的事情上用鏈。

三個最大的數字

結構定義 80 → 16 個(協議裡需要精確定義的資料格式數量)
每指令鏈上狀態讀取 233 → 48 次(執行一個鏈上操作要讀多少筆資料)
簽名物件 13 → 3 種(需要密碼學簽名的東西)

一個誠實的反例

行數只降 26%,而且中途一度上升(第一版草稿只有 1,390 行)。原因是:每一輪審查都在 刪機制、加散文——補上「這條規則為什麼存在」「它擋掉哪個分歧」「哪一版草稿寫錯了」。 那些散文正是後面幾輪能分辨「承重的規則」和「裝飾的規則」的依據。機制在減少,說明在增加。

①系統概觀:CBQS 是什麼、由誰使用

什麼是「訊息佇列」

想像一個餐廳的出單機。服務生把點單貼上去,廚師一張一張撕下來做。點單機讓兩邊不必同時在場: 服務生不用等廚師有空,廚師忙完再來拿下一張。

類比:出單機

訊息佇列就是軟體版的出單機。生產者(producer)把訊息放進去,消費者(consumer) 取出來處理。這樣兩邊可以獨立擴容、獨立故障、獨立重啟,而不會互相拖累。

CBQS 要解決的具體場景:Cowboy 上的 runner(執行 AI 任務、HTTP 請求的鏈下程式)之間 需要互相傳工作訊息,而這些訊息不適合塞進區塊鏈——太大、太頻繁、太不值錢。

四個角色及其邊界

Owner 擁有者在鏈上持有這條佇列的人。他付錢,他決定誰能用。
Provider 服務商實際跑伺服器、存資料、送訊息的人。他收錢。
Broker 中介程式Provider 跑的那個伺服器程式(cbqsd)。技術上做事的就是它。
Holder 憑證持有者拿到 owner 簽發的授權、實際來讀寫訊息的程式。
這個區分為什麼重要

因為付錢的人、做事的人、用的人可以是三批人。owner 可能是一家公司,provider 是它租的 服務商,holder 是它自己的十個微服務——每個微服務拿到的權限還可以不一樣(有的只能寫、有的只能讀)。 規格必須說清楚每一條規則約束的是誰。

「鏈上」與「鏈下」的區別

鏈上(on-chain)= 寫進區塊鏈的資料。全世界每個驗證節點都要存一份、都要算出一模一樣的結果。 好處是不可竄改、有公信力;壞處是又貴又慢。

鏈下(off-chain)= 普通伺服器上的資料。快、便宜,但要信任跑它的人。

類比:法院與倉庫

鏈就像法院:適合登記「這間倉庫是誰的」「租金付到幾號」。你不會把每一箱貨物進出都去法院公證一次—— 那既沒必要,也癱瘓法院。

v1 的問題正是如此:它每搬一箱貨都去法院蓋章。v2 把法院的職責收回到 「誰擁有、誰服務、有沒有付錢、誰被授權」這四件事上。

②術語定義

stream串流 / 佇列

一條訊息佇列本身。CBQS 的基本單位,一個 owner 可以有很多條。

lane通道

串流內部的分類標籤,像同一個出單機上分「冷盤/熱炒/甜點」。不是獨立佇列——所有 lane 共用 同一個總順序。

record / sequence記錄 / 序號

一則訊息叫 record。每則有一個嚴格遞增的整數 sequence,從 0 開始,不跳號、不重用。

consumer group消費者群組

一組互相搶訊息的消費者。同一則訊息在一個 group 內只會交給其中一個成員處理,但不同 group 各自都會拿到一份。

lease租約

訊息交給某個消費者時發的「暫時歸你處理」憑證,有時限。超時沒回報就收回重派——這樣消費者當機 訊息也不會卡死。

at-least-once至少一次

保證訊息至少被送達一次,但可能重複。因為「剛好一次」在分散式系統裡代價極高, 業界標準做法是至少一次 + 消費端自己去重。

idempotent冪等

同一個操作做兩次和做一次結果一樣。例如「把餘額設成 100」是冪等的,「餘額加 10」不是。 收到重複訊息不出錯的關鍵。

durable commit持久化提交

資料真的寫進硬碟(而不是還在記憶體快取裡)。斷電也不會丟。代價是慢——這是 v1/v2 的一個關鍵取捨點。

consensus state共識狀態

鏈上所有節點必須完全一致的那份資料。每讀一次、寫一次都要計價,而且兩個實作算出不同結果 = 分叉,是最嚴重的 bug。

governance parameter治理參數

可以透過鏈上治理投票調整的設定值(例如「一條串流最多幾個 lane」)。v1 有 56 個,v2 剩 31 個。

grant授權憑證

owner 用鏈上金鑰簽發的一張「許可證」,寫明持有者能做什麼(讀/寫/管理)、能碰哪些 lane、有效到何時。

snapshot鏈狀態快照

broker 定期從鏈上抓一份資料副本。v2 用它取代「每個請求都即時讀鏈」。

Merkle proof默克爾證明

一種密碼學技巧:能證明「某筆資料確實在一大堆資料裡」,而不用把整堆都給對方看。v1 用它做 per-lane 證明,v2 拿掉了。

HPKE / 端到端加密

一套標準加密方法。v1 讓平台幫使用者管金鑰和加解密;v2 不碰——應用自己加密好再丟進來。

CRDT無衝突複製資料型別

一種能讓多人同時編輯、事後自動合併不衝突的資料結構(例如協作文件)。v1 的 fast 類別是為它設計的。

escrow託管餘額

預先鎖在鏈上、用來付租金的錢。v1 每條串流一份,v2 改成每個 (owner, provider) 關係一份。

backpressure背壓

接收方告訴發送方「我來不及了,慢一點」的機制。沒有它,慢的消費者會被塞爆。

dead-letter queue死信佇列

處理失敗太多次的訊息被丟進去的地方。v2 把整套拿掉了(原因見第 ⑨ 節)。

conformance一致性(符合度)

一份「怎樣才算正確實作了這個規格」的可測清單。v1 完全沒有,v2 新增了一整章。

gas / metering計量

鏈上每個操作要收多少運算費。必須逐位元組精確,因為兩個節點算出不同的 gas 就是分叉。

③核心觀念:鏈為什麼不在資料路徑上

這一節單獨成節,因為後面約八成的變更都是它的推論。

圖:v1 把鏈放在訊息必經之路上(上),v2 把鏈移到旁邊、只定期同步(下)。 這一個改動就決定了後面大部分的刪除。
v1 的實際代價

每傳一則訊息,端到端要付:2 次客戶端簽名 + 2 次 broker 驗簽 + 2 次同步寫硬碟 (一組給寫入、一組給確認),外加一次鏈上共識狀態讀取。

更糟的是 v1 有個參數叫 cbqs.max_chain_staleness_blocks——鏈只要落後超過這個值, broker 就拒絕服務。也就是說鏈打噴嚏,整個訊息佇列跟著感冒。

v2 怎麼做

broker 定期(預設 2 秒)抓一份鏈狀態快照,一個請求就從一份快照判斷到底。客戶端開 session 時驗一次簽名,之後 session 內的請求都不帶簽名。

代價寫在文件裡:撤銷授權不再是即時的。它被兩個東西界定——正常情況是快照刷新間隔, 最壞情況是憑證本身的到期時間。規格明說這一點,而不是暗示更強的保證。

⑤變更一:鏈退出資料路徑

1.1 授權方式:每請求驗簽 → 一次性 session

v1

每個請求(連讀取都算)都帶一個 RequestProofV1 簽名,broker 對著即時讀取的鏈狀態驗證。鏈太慢就整體停止服務。

v2

開 session 時驗一次授權憑證,之後 session 內請求不帶簽名。 broker 用定期快照判斷,鏈不可用時繼續服務既有 session。

為什麼

這同時是吞吐量天花板和可用性地板。而且撤銷授權本來就不需要 即時讀鏈——它需要的是「延遲有上界」,定期刷新就能給。

代價

撤銷不再即時。上界:正常是快照刷新間隔,最壞是憑證到期。 規格明寫。

1.2 收據:每則訊息一張 → 每批一張

v1

每次寫入回傳一張 broker 簽名的收據,串進全域和 每個 lane 兩條雜湊鏈。連 Ack/Nack/Extend/Reject/Redrive 和群組變更都各自有收據和自己的鏈—— 共 12 種帶收據的動作。

v2

每個持久化批次一張 CheckpointReceiptV2, 用一個扁平摘要涵蓋整批,再用連續性規則把批次串起來。訊息路徑上零非對稱密碼學。

為什麼

批次提交(group commit)是所有主流訊息中介達到高吞吐的辦法。 而且更細的證據沒有東西去消費它——v1 自己的信任模型就寫明沒有爭議仲裁、沒有質押、沒有罰沒。 證據再細也沒有人能拿它去執行什麼。

代價

證據粒度從「單則訊息」降到「一個批次」。而且只持有批次 一部分的人根本無法驗證——v2 把這句話明寫出來,而不是讓人誤以為有逐則證明。

⑥變更二:計價從「按量」變「按條」

類比:水錶 vs 月租

v1 像裝水錶:按流量、按存量、按頻寬三種單位分別計價,還分兩種資費方案(標準/快速), 每種三個單位、每個單位兩個參數——光資費表就 12 個 鏈上凍結參數。

v2 像收月租:一條串流每個區塊固定多少錢,不管你傳多少。

v1

一條簽名報價路徑 PriceQuoteV1 加上一套 管理式資費表(12 個凍結參數)。託管餘額每條串流一份,有停權寬限期,租金還要扣掉鏈暫停的時間。

v2

一個 cbqs.stream_rate_per_block,從一個 按 (owner, provider) 記帳的預付帳戶扣。沒有報價、沒有資費表、沒有每串流託管、沒有寬限期、 沒有暫停時鐘。

為什麼

那些計量單位在計價「broker 本來就會用上限擋住」的容量—— 同一份風險被兩套機制各擋一次。而兩條資費路徑意味著兩套准入規則、兩種失敗模式、兩組錯誤碼,只為回答 同一個問題:這條串流這個區塊可不可以存在?

代價

provider 無法對重負載的串流收更多錢。它的風險改由 §15 的每串流上限和它自己的 max_streams 界定,而不是靠價格。

− ActivateKeyGeneration− SetProviderStatus− SettleStreamRent − TopUpStream+ SettleAccount+ TopUpAccount + WithdrawAccount

設定值也離開了鏈

v1

StreamConfigV1:12 個欄位的保留期、訊息大小、 交付與加密設定,存成共識狀態,改一次要送一筆鏈上交易。

v2

5 個 broker 端設定,每個在接受時對治理上限檢查一次。 鏈上記錄只剩 9 個欄位,沒有一個是設定、沒有一個是錢。

為什麼

這些東西不需要在兩方之間仲裁——它是 owner 和它的 provider 之間的約定。放進共識只是讓每次調參都變成一筆交易。鏈真正該仲裁的是:誰擁有、誰服務、 哪把金鑰能授權、有沒有付錢。

⑦變更三:四個子系統整個下架

這四個都是延後到後續 CIP,不是宣告不需要。判斷標準每次都一樣: 這個機制偵測或防止的東西,文件其餘部分有能力處置嗎?

3.1 fast 快速交付類別

v1 · 提到 109 次

第二種交付類別,有暫定確認、broker 世代、 FastLineageV1 血統追蹤、Clean/Void 兩種世代轉換語意、暫定與持久兩條水位線, 外加一整套規範性的 CRDT 重新同步程序。

v2 · 提到 1 次

只有一種交付類別。那 1 次出現在「被移除了什麼」的清單裡。

為什麼

在還沒有任何使用者之前,一份文件裡就放了兩套持久性模型、 兩條當機復原路徑、兩種識別碼形狀。

代價

這是真的退步,而且文件明說:協作游標、線上狀態這類 workload 要多付一個批次窗口(約 20 毫秒)的延遲。這是最可能第一個被要求加回來的東西。

3.2 Lane 分區的 Merkle 證明

v1 · 約 400 行

兩種樹演算法(含奇數節點提升規則和一段關於長度歧義 的論證)、固定深度 256 的稀疏樹、bitmap 證明、規範化下降路徑、每批次的每 lane 存在與不存在證明、 遺漏偵測、兩種驗證模式。

v2 · 1 句話

每批次一個扁平摘要,外加一句「lane 範圍的訂閱者 無法驗證 checkpoint」。

為什麼

這套機制偵測的是真實存在的缺陷(provider 偷偷漏送某個 lane 的訊息)。但 v1 裡沒有任何東西能處置這個偵測結果:沒有爭議機制、沒有質押、沒有罰沒。 v1 自己對「provider 出問題」開的藥方是「換一家」。偵測得到但無法追究,等於沒有。

代價

明說不藏:lane 範圍的驗證不可用,變通辦法是「一個驗證域 開一條串流」。要加回來,應該和讓偵測有意義的爭議機制一起加。

3.3 平台加密、金鑰串流、CBSS 託管

v1 · 加密 36 次 / CBSS 18 次

HPKE 信封、每條資料串流配一條金鑰 串流、分塊上傳的金鑰輪替批次(自帶收據)、成員變更語意、一個專屬鏈上指令 ActivateKeyGeneration、CBSS 門檻式根金鑰託管,以及 5 個金鑰批次參數。

v2

payload 就是不透明的位元組。應用自己管金鑰。 broker MUST NOT 解讀 payload 內容。

為什麼

把機密性做成平台服務,等於讓協議負責金鑰保管、輪替、 成員管理三件各自都有成熟獨立解法的事,還把佇列的發布時程綁在 CBSS 上。而應用自己先加密再丟進來, 拿到的保證更強——因為 broker 從頭到尾連金鑰都沒碰過。

代價

原本想從平台拿到金鑰管理的應用要自己做。§2 把 「payload 機密性」明列為非目標,免得有人誤會。

3.4 簽名的保留期錨點 + CBFS 歸檔

v1

三種簽名錨點物件,外加把被淘汰的記錄歸檔到 CBFS。

v2

一個「保留下限序號」,透過一個錯誤碼的 payload 觀測: CursorTooOld 帶一個 u64。

為什麼

錨點是「對一個你問一下就能知道的數字做簽名聲明」。 簽它等於為了證明一件沒有人在爭議的事,多加一個物件、一條鏈、一條驗證路徑。

⑧變更四:五個「在補償更下層選擇」的機制

這五個有個共同形狀:它們本身沒錯,但它們存在的唯一理由是補償一個更底層的設計選擇。 把那個選擇改掉,它們就沒事做了。

  • 端點驗證離開共識。v1 在鏈上准入時跑一套五條規則的演算法(禁用位元組掃描、逐位元組的 scheme 比對外加兩段勘誤、WHATWG URL 解析、私有網段檢查)。v2 直接收下 URI 不解析,把位址檢查交給 客戶端——因為只有客戶端知道它即將連到哪裡。共識不可能知道一個主機名在連線當下解析到哪, 假裝知道等於在狀態機裡開了一個 DNS 形狀的洞。
  • Lane 不再背負協議機制。v1 把客戶端選的 nonce 雜湊成 lane id,於是需要:一個永久墓碑集合 (防止舊 id 被重建成不同歷史)、一個對墓碑集合的上限、一個防止有人霸佔命名空間的速率限制,以及當 兩個上限同時滿了會卡死的處理。v2 改成 broker 指派的單調遞增整數,重用在構造上就不可能, 前三個直接消失。第四個(建立速率限制)留下來但換了範圍——因為指派解決了「霸佔」, 沒解決「在固定月租下大量產生持久狀態」的成本。
  • 一個指令一個事件。12 個事件變 8 個,每個成功指令一個,發布狀態值而不是狀態變化。 v2 明說後果(想知道某次結算是停權還是復權,自己 diff 前後區塊的帳戶狀態),而不是宣稱兩者等價。
  • 應用指引離開規格。v1 的 Homestead 章節用規範性語氣描述一種應用模式。 指引不是協議要求,一致性測試也測不了它。
  • 依賴從 8 個 CIP 降到 3 個。CIP-9(CBFS)、CIP-24(CBSS)、CIP-36,以及 CIP-2/CIP-10 作為 硬依賴,都隨著對應的表面一起消失。

⑨變更五:v2 拿自己開刀砍掉的四個

前面所有變更都是「v2 對照 v1」。這一節不同——這四個是v2 的草稿寫出來之後,經過對抗式審查 才被砍掉的。每一個都帶著一個「修下去只會讓文件變長」的缺陷。

5.1 broker 端去重

為什麼

四版草稿試著給這個存放區設上界,每一版都生出下一個缺陷。 最後一版用「單調下限」,結果它拿客戶端的時鐘去比broker 的時鐘——在完全合規的輸入下 放進了一則重複訊息,正是這個存放區存在要防的事。§9 把責任放回「至少一次交付」本來就要求的地方:消費端。

5.2 死信佇列與 Redrive

為什麼

草稿自己承認這個佇列無法檢視、只能盲抽。 那它就只是「蓋在 log 已經按序號索引好的同一批位元組上的第二個索引」,卻自帶 TTL、自帶治理參數、 自帶分頁上限、自帶一個和保留下限打架的回收期限,還有一個計數器——那個計數器存在的唯一理由, 是讓被重驅的記錄能排到後來的記錄後面。

代價

只想拿失敗訊息的消費者,改成按序號重放 log,而不是抽一個佇列。

5.3 StrictFifo 嚴格順序模式

這是最值得看的一個

StrictFifo 模式只暴露「最低的未終結項目」。而保護共用群組的那個上限 max_in_flight_per_holder 最小值是 1——在 StrictFifo 下它等於沒有保護。

後果:一個只拿到 CONSUME(最弱的消費權限,連終止都做不到)的持有者, 取走那唯一一個租約、然後什麼都不做。租約超時十次,那則訊息就走進終態。 然後換下一則。整個共用群組的每一則訊息,都可以被一個「開了訂閱之後一個位元組都沒再送」的人毀掉。

代價

想要順序處理的群組,改用「一個排序域一條 lane」,而不是一個模式旗標。

5.4 Nack 的延遲參數

為什麼

它讓 §6.2 豁免於償付能力檢查的動作,能買到 §6.2 管制的動作的 120 倍生命期——直接推翻該節自己的判準。現在 Nack 在 「沉默超時本來就會釋放的那一刻」釋放,所以它不移動任何期限,而且主動回報永遠不會比不吭聲更糟。

⑩v2 新增的東西(簡化不只是減法)

下面前三項,v1 完全沒有對應章節。

  • 一致性章節(Conformance)。v1 沒有。§19 說明「怎樣才算正確實作」,並且另外列出哪些要求 是從外部觀測不到的——這樣讀者能分辨「可稽核的保證」和「只能靠信任的義務」。
  • 啟用章節(Activation)。v1 沒有。§18 說明啟用是重置、用封閉世界規則讓 genesis 拒絕 所有 v1 參數(不必逐一列舉),並釘死儲存格式標記鍵,讓 v2 的 broker 打不開 v1 的資料庫。
  • 釘住的 gas 向量檔案。27 條向量涵蓋每個鏈上指令的每個分支,用 SHA-256 釘在 §15.1 裡, 逐條寫明計費的讀、寫、cycles、cells。兩個驗證節點算出不同 gas 就是分叉,v1 把這件事留給散文。
  • 預付帳戶物件與提領路徑。錢從串流記錄搬走之後,總得有地方放、有辦法拿回來。
  • 運維面(§17)。定義 /readyz、/statusz、/metrics, 其中包含一條關鍵規則:鏈快照刷新失敗 MUST NOT 讓 broker 變成未就緒——這條規則才讓 「資料面獨立於鏈」在實務上成立(否則負載平衡器會把還能服務的 broker 全部摘掉)。
  • 新的 STREAM_ADMIN 權限位元,用 v1 留空的那一位,授權那些取代了鏈上設定的 §13 設定變更。

⑪刻意保留的,以及明說沒關掉的

保留

  • 鏈控制的授權。用鏈上管理金鑰簽發、帶世代計數器的憑證。沒有它,CBQS 就只是一個 「自己維護客戶名單的中介軟體」,而不是 Cowboy 的服務。
  • 帶同意權的 provider 註冊表。accepts_new 和 max_streams, 讓一個無需許可的註冊表不能把 provider 塞爆。
  • 至少一次語意,精簡到工作佇列真正需要的部分。租約、可見性超時、嘗試次數、每持有者的 在途上限、四個租約動作。
  • 信用額度式背壓(背壓必須是明示的),以及先持久化再確認(否則就是靜默丟失)。

明說沒關掉的四個限制

為什麼要寫出來

因為藏起缺口的規格,比明說缺口的規格更危險。每一條都寫在它實際會咬人的那一段旁邊。

  • 沒有 broker 身分認證。握手只認證客戶端。網路位置攻擊者(DNS/BGP 劫持、誤發憑證) 事後可偵測(provider 對每張 checkpoint 簽名)但無法預防;鏈上帳戶被攻陷的話, 攻擊者一個指令就同時換掉端點和金鑰,只能部分偵測;兩者都不能防「中繼整個握手」,那需要這份文件 沒有定義的通道綁定。
  • 兩條速率上限有關聯但不強制。扇出(一則訊息要送給 N 個群組)意味著交付預算必須是寫入預算的 某個倍數,§13 把不等式寫出來但不驗證。
  • 被拒絕的寫入,其回應會放大流量。12 位元組的請求配一個最大 2,093 位元組的錯誤回應。 這是可以用計費規則關掉的,但沒關。
  • 出向流量沒有 per-holder 範圍(入向有兩層),而公平排程規則是 per-connection, 但連線數本身是運維問題不是協議問題。

⑫怎麼啟用:重置,不是遷移

為什麼可以直接重置

CBQS 從來沒有在一個「狀態必須被保留」的網路上啟用過,而且 v1 自己就把自己規定為 「僅限重置、發布前」。所以不需要遷移路徑——這是一個難得的、可以乾淨切換的時機。

genesis 只種預設值種下註冊表單例和每個參數的預設值,拒絕任何 v1 的參數鍵。
解碼器認版本位元組不是 2 的一律拒絕,鏈上 payload 和儲存的記錄都算。
儲存格式標記v2 的 broker 打不開沒有 v2 標記的資料庫,不會做部分解碼。
運維禁令不得把 v1 的鏈狀態、broker 資料庫或封存快照帶過這條界線。

§18 特別用了封閉世界的寫法:「genesis MUST 拒絕任何 §15 的表格沒有列出的 cbqs.* 鍵」。這樣就不必逐一列出 v1 的參數——一個驗證節點不需要知道 v1 存過什麼,就能拒絕它。列舉會過期,規則不會。
