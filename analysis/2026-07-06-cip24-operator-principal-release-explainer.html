Operator-Principal 釋放類 — 解讀與原理

TL;DR一分鐘導讀

CIP-34 demo 裡,operator(部署者)的伺服器 server.js 把一把簽名私鑰 明文存在 .cowboy/key,每次幫用戶簽交易都用它。硬碟被偷 = 金鑰永久失竊。

這份修正案讓這把金鑰改由 CBSS 密碼學委員會保管:平時鏈上只有一份加密封套,伺服器要簽名時,臨時向委員會請求「釋放」,用完即抹除。好處是:金鑰不再明文落地、可撤銷、有門檻保護、有審計軌跡。

🔑 一句比喻
現況像把家門鑰匙用膠帶貼在門口——誰路過都能撕走複製。這份修正案把鑰匙換成:平時鎖進需要 5 人裡 4 人同時點頭才能開的保險庫,你要用的時候才臨時取出,而且庫房會記帳、你隨時能吊銷取用權。
但注意:鑰匙取出來的那一刻還是會出現在你手上——這一點任何保管服務都躲不掉,除非用 TEE 保險箱(見 第 ⑤ 節)。
📎 這份解讀檔涵蓋兩份東西
你若完全沒接觸過 CBSS,請從 第 ② 節開始——那是 CIP-24 原始文檔(CBSS 全系統)的從零導讀。第 ② 節把整套系統講清楚後,第 ③ 節再說明本修正案與 CIP-24 是「附加/互補」關係,以及它往原文檔的哪些章節插入了什麼。第 ④ 節之後才是修正案本身。

①問題:金鑰躺在硬碟上

Cowboy 上有一類越來越常見的角色:常駐的鏈下服務(standing off-chain service)。它握著一把長壽命的簽名金鑰,持續不斷地用它——不是為了某一筆「工作(job)」,而是它的日常。典型例子:

  • CIP-34 聊天 demo 的 operator/deployer:server.js 幫每個用戶請求簽 Cowboy 交易。
  • 跨鏈 bridge relayer:握著一把 EVM 金鑰。
  • 幫 actor 轉接 LLM / API token 的服務。

今天它們的金鑰都明文存在單一機器上。這帶來三個結構性弱點:

維度明文存硬碟(現況)
靜態風險硬碟 / 備份 / 快照被偷 = 金鑰永久失竊
撤銷做不到——金鑰是可複製的死物,偷走就收不回
審計零軌跡——不知道被用過幾次、誰用的

那為什麼不直接套用 Cowboy 現成的秘密管理系統(CBSS)?因為 CBSS 現有的兩條釋放路徑都不接受這種角色——這正是本修正案要補的縫。要看懂縫在哪,得先懂 CBSS 怎麼運作。

②CIP-24 / CBSS:從零開始的全景

這一節完全獨立——把 CIP-24 原始文檔講清楚。看懂它,才看得懂修正案補了什麼。

CBSS(Cowboy Secret Service)就是 CIP-24 這份規格定義的系統:一套「門檻式秘密釋放」服務。核心是一組經過質押的 proxy 運營商組成的委員會,預設 5 個成員、門檻 4(記作 (n,t)=(5,4)),住在系統位址 0x04。

它原本要解決什麼問題

Cowboy 是個「AI 原生」的鏈:鏈上的 actor(智能合約)常常需要呼叫鏈下的東西——LLM、HTTP API、MCP 工具。這些呼叫幾乎都需要一把密鑰(OPENAI_API_KEY、SLACK_TOKEN、STRIPE_LIVE_KEY…)。

🎯 兩難
密鑰不能明文放上鏈(鏈上資料全公開);但實際去呼叫 API 的是鏈下的 runner,它必須在某個瞬間拿到明文密鑰才能發請求。怎麼把明文只在「該用的時候、交給該用的人」?這就是 CIP-24 要解決的問題。

CIP-24 的答案:密鑰以加密封套存在鏈上,真正的解密能力被切成碎片、分散在委員會手裡。只有當一個「被授權的請求」到來,委員會裡足夠多的成員才會各自吐出一片,讓請求方臨時組出解密能力、用完即抹。沒有任何單點(包括委員會裡的少數幾人)能私自解出密鑰。

一個秘密的完整生命週期

以「actor 要用 SLACK_API_KEY 發訊息」為例,從頭到尾:

① 存(SetSecret)owner 產生一把資料金鑰 DEK,用委員會主公鑰 MPK 做 IBE 加密,得 wrapped_dek 存上鏈;密文本體存 CBFS(分散式儲存)
② 授權actor 的 CIP-6 manifest 宣告 secrets.read: [SLACK_API_KEY];owner 設 SecretPolicy 允許哪些 actor
③ 請求actor 執行到 runner.http(..., secrets=[...]),被指派的 runner 用自己的註冊金鑰簽一份釋放請求
④ 委員會釋放runner 發給 4/5 個 proxy,每個 proxy 校驗(§3.7)後吐出一片 partial σ_i
⑤ 組合 · 解密 · 使用runner 組出 σ → 解出 DEK → 從 CBFS 解出明文密鑰 → 填進 HTTP 請求發出
⑥ 抹除 · 記帳runner 把明文/DEK/σ 歸零;每個參與的 proxy 各自提交一份鏈上 release_receipt(付款 + 審計)

三個外部系統在這裡協作:CBSS(0x04)管授權與委員會,CBFS(CIP-9)存加密密文,runner(CIP-2)是鏈下執行者。密鑰明文只在 runner 沙箱裡、只在步驟⑤那一瞬間存在。

委員會 · DKG · 為何不是「重建金鑰」

🏛 委員會怎麼「共同持有」一把主鑰
透過 DKG(分散式金鑰生成),5 個成員各自持有主秘鑰 MSK 的一「片」share。任何 4 片可以聯合完成一次密碼運算;3 片以下什麼都做不了。沒有任何單一成員、甚至任何 3 人小圈子,能單獨還原 MSK。
底層是 BLS12-381 曲線上的門檻 IBE(Boneh–Franklin)+ tlock,drand / Filecoin / 以太坊生態的成熟庫。CBSS 自己不造密碼學。

為何不是「把金鑰重建出來」,而是「釋放一個 token」

這是最容易誤解的一點。委員會不會把你的秘密拼回來再交給你。實際流程是:

  • 你的秘密(DEK,資料加密金鑰)在鏈上是一份 IBE 加密封套 wrapped_dek,綁定到一個「身分」I(由 秘密ID + 版本 + wrap_epoch 算出)。
  • 要解封,需要對這個身分 I 的一個門檻簽章 σ = MSK·I。
  • 委員會每個成員只吐出自己的一「片」partial σ_i = s_i·I;請求方蒐集 ≥4 片,用 Lagrange 內插自行組出 σ,再本地推導出解封金鑰、解出 DEK。
🧩 比喻
委員會不是「保管你的鑰匙」,而是「4 個人各自在你這份特定文件上蓋一個章;4 個章湊齊,文件才能打開」。他們蓋的章只對這一份文件(這個身分 I)有效,換一份就得重蓋。所以委員會從頭到尾沒看過你的明文秘密。

機密釋放那扇門,要求請求者是「被 dispatcher 指派到某個 job、且該 actor 的 manifest 宣告了 secrets.read 權限」的 runner。時間鎖那扇門則是「到點對所有人公開」。這兩扇門是 CIP-24 原始文檔已經有的全部釋放方式。

信任模型:靠「不合謀 + 質押」,而非硬體

CIP-24 有一個刻意的設計選擇:它的信任根不是 CPU 廠商的 TEE(可信硬體),而是 t-of-n 的經濟賽局。

TEE-rooted 釋放CBSS(CIP-24 選這條)
信任根CPU 廠商證明(Intel/AMD)t-of-n proxy 不合謀 + 質押罰沒
失效模式TEE 被破 → 所有秘密可回溯外洩t 人合謀 → 僅其任期內觀察到的秘密
硬體需求需 TEE 硬體一般硬體
🛡 這代表什麼
要偷一把秘密,攻擊者得同時攻陷 5 個裡的 4 個特定 proxy(且它們分屬不同司法管轄、軟體版本、組織)。委員會成員還會定期 reshare(輪換手中的碎片、換血成員),提高「必須同時、持續」合謀的難度。任何洩露披露後,治理可罰沒質押並永久除名。TEE 在 CIP-24 裡是可選的加分項(tee_required),不是信任根——這一點在修正案裡會再遇到。

③本修正案 ⟷ CIP-24 是什麼關係

✔ 一句話:附加(additive)/ 互補,不是替代
這份草稿是 CIP-24 的一個「v1 amendment(修正案)」。它不改動、不移除 CIP-24 任何既有內容;它插入一種新的釋放模式,並完全重用第 ② 節講的委員會、DKG、密碼學、封套。原本的 runner 路徑與 tlock 路徑原封不動。

換句話說,第 ② 節那套 CBSS 系統照舊運轉;這份修正案只是在它旁邊多開一扇門,給一種 CIP-24 原本服務不到的角色(常駐 operator 服務)。因為修正案的章節本身就是「插進 CIP-24 §3.1 / §3.5 / §3.7 …」,所以它離開 CIP-24 無法獨立存在或理解——這就是為什麼這份解讀檔必須先講完整個 CIP-24。

它往 CIP-24 的哪些地方插入了什麼

CIP-24 章節修正案做的事性質

由此可見:修正案的「爆炸半徑」被刻意限制在授權層。唯一的跨倉牽動是可選的 TEE 路徑(§6a),所以預設(非-TEE)路徑是可獨立發布的核心。這也是 Marshal 審計反覆確認的一點:密碼學中立。

那,為什麼原本兩扇門不夠?

回顧第 ② 節結尾:常駐 operator 服務不是被指派的 runner(沒 job、沒 dispatcher、不是部署的 actor),也不是「到點公開」的 tlock 消費者(它的金鑰必須始終保密)。兩扇門都不接受它——所以需要第三扇門,這正是下一節。

誰job 裡的 runner

⏰ 時間鎖

認證無(公開)

🧑‍💼 Operator-Principal新

域cbss/ibe/v1(同機密釋放)
認證鏈上 Grant + K_auth 簽名
誰owner 註冊的常駐服務

核心洞見:這是純授權層變更,不動任何密碼學

新的這扇門,釋放的是一個普通的機密秘密(operator 的簽名金鑰)。因為它始終保密,所以必須留在跟機密釋放同一個身分空間 cbss/ibe/v1——重用委員會既有的 MPK、shares、DKG,加密封套格式一字不改。

✔ 與 tlock 的關鍵分野
tlock 之所以需要另開一個域 cbss/tlock/v1,是因為它的金鑰到點會變公開——必須跟機密秘密的身分空間隔離,免得公開釋放意外解出機密。
而 operator 金鑰永遠不公開,所以不需要新域。它變的只有一件事:誰被授權請求釋放、以及他怎麼認證自己。密碼學(配對檢查、身分綁定、封套)完全沒動。

具體來說,新的授權方式替換掉舊機密路徑的「三件套」:

機密釋放(runner 路徑)需要…→Operator 路徑改成…
dispatcher 把 runner 指派到某 job→一張鏈上憑證 OperatorReleaseGrant
+ 用 K_auth 簽的請求
actor 的 CIP-6 manifest 宣告 secrets.read→
SecretPolicy.actors 允許該 actor→

三金鑰分離:把「一個檔案」拆成三種溫度

現況把三種角色全塞進一個 .cowboy/key 檔。這份修正案刻意把它們拆開:

K_root
🧊 冷 · 離線

帳戶根金鑰。負責發放/撤銷憑證(Grant)。平時離線收好,幾乎不動。

K_auth
🌡 暖 · 在服務上

釋放授權金鑰。常駐服務用它對每次釋放請求簽名。它只能授權釋放,不是簽名金鑰本身,也不能控制帳戶。

K_sign
🔥 瞬時 · 用完即抹

被保管的秘密(真正的簽名金鑰)。平時是鏈上加密封套;要用時才臨時重建在記憶體,用完立刻抹除。

💡 為什麼這樣分很關鍵
暴露在網路上的暖服務,手裡只有 K_auth——既不是帳戶根金鑰,也不是(靜態的)簽名金鑰。
K_auth 若被偷,攻擊者拿到的是「限速、可撤銷、有審計的釋放能力」,不是金鑰檔本身,也不是帳戶控制權。這比現況「偷走檔案 = 永久竊得金鑰」窄得多。

授權憑證:OperatorReleaseGrant

owner 用冷金鑰 K_root 在鏈上(0x04)發一張憑證,指名「哪個暖金鑰 K_auth 可以釋放我的哪個秘密」。它是「actor manifest 權限 + ACL + job 指派」三件套的帳戶版對應物,收攏成一張 owner 簽發的記錄。重點欄位:

secret_id — 你自己的秘密 auth_pubkey — K_auth 公鑰 version_pin — 釘版本 or 跟隨最新 tee_required — 是否要 enclave max_releases_per_hour — 限速 expiry — 自動過期
⚠ 一個刻意的邊界:僅限本帳戶
Grant 只能授權自己帳戶的秘密(secret_id.account == 發起人)。不像 ACL 可以跨帳戶授權給別人的 actor——這是為了避免 operator 路徑變成第二條、更弱的跨帳戶通道。

常駐拉取流程(一次簽名發生了什麼)

服務需要簽名例如要簽一筆 Cowboy 交易
組請求 + K_auth 簽名帶 nonce、鏈高度、目標 epoch
發給 4/5 個 proxy每個 proxy 依 §3.7.1 校驗憑證
收集 partials 組 σ本地 Lagrange 內插
解出 K_sign推導金鑰 → 解封 DEK → 取 CBFS 明文
簽名 → 立刻抹除K_sign、DEK、σ 全部歸零

與 runner 路徑相比,唯一差別是:沒有 dispatcher 查詢、不用 runner 註冊金鑰——principal 就是 operator 的常駐服務,用 K_auth 認證。而所有密碼學驗證步驟(配對檢查、recipient 一致性、去重、quorum 上限、付款)與 runner 路徑逐位元組相同。付款從owner 帳戶扣,每個 proxy 收一次費,上限為門檻 t。

⑤誠實的限制:這扇門不能做什麼

這份草稿刻意不誇大。三個限制必須講清楚,否則會給人虛假的安全感。

🔥 限制一:保管不消除「瞬時重建」
簽名發生的那一刻,K_sign 必然被重建在服務自己的記憶體裡——門檻釋放的本質就是「把明文交給被授權的請求方」。此刻若主機被入侵,攻擊者仍看得到它。
只有 TEE(tee_required)能移除這一點:讓重建發生在enclave 保險箱內,明文不進主機記憶體。所以這份修正案在預設路徑上只敢宣稱「消除明文靜態存儲 + 可撤銷 + 門檻保護 + 審計」;「消除瞬時重建」是有條件的,而且那個 TEE 路徑本身是一項尚待落地的跨倉依賴(見審計 F7)。
⏳ 限制二:撤銷是「停未來」,不是「retroactive 封印」
撤銷 Grant 後,在 finality + proxy 快取 TTL 這段窗口內,若所有 4 個 proxy 都還握著陳舊快取,攻擊者仍能湊齊一次完整釋放——鏈端的撤銷檢查只擋付款,擋不住重建。
更關鍵:K_sign 是長壽命金鑰,只要被釋放一次就永久洩露。撤銷只能停下一次釋放,不能讓已洩露的金鑰復原。正確的事故處置是輪換 K_sign(部署新版本)+ 撤銷,兩者都做。
💸 限制三:限速是「成本/騷擾」界,不是「金鑰暴露」界
max_releases_per_hour 是 proxy 本地、鏈下、諮詢性的——鏈上不強制。它管的是花錢和騷擾,不是金鑰暴露(反正一次釋放就已洩露)。而且它雙面刃:若把限速設成服務真實簽名速率,被偷的 K_auth 可以燒光額度,讓誠實服務簽不了名 → 甚至拖累帳戶進入 delinquent、全帳戶 JobSubmit 被拒。硬性的鏈上界其實只有 overdraft 上限。
✔ 淨結論
這扇門把「永久、無聲、不可撤的金鑰失竊」變成「可撤銷、有審計的釋放能力」——是實打實的進步。但代價是:撤銷有個有界的完整釋放寬限窗、長壽金鑰洩露後必須輪換而非只撤銷、以及 K_auth 濫用下的一種可用性故障。它不會讓一個暴露在網路上的簽名服務變得無條件安全。

⑥壓力測試:Marshal 深度審計

這份草稿經過 Marshal(分級 + 對抗式 review + 逃逸棘輪的本地質量門禁)深審,兩路獨立對抗式審查(自審 + 獨立 reviewer 各一遍,預設懷疑、專攻機密性/授權這種「不變量測試抓不到」的否定性屬性)。結論收斂:

✔ 核心判定:密碼學中立性穩固,無 HIGH
真·授權層純變更、正確重用 cbss/ibe/v1、保留 recipient/配對/去重共識檢查。無共識分叉、無金鑰混淆漏洞。被駁倒的攻擊假設:跨協議簽名重放、release_id 碰撞、recipient/MPK 混淆、determinism fork。
真正的弱點不是密碼學,是「宣稱的準確性」——以下 6 條已全部折進修訂版。
F7MED ↗TEE 路徑是未言明的跨倉 schema 變更

草稿把 tee_required 說成「keyed by grant_id / 復用 §9.5」,但現行 0x05 的 attestation 記錄與簽名載荷全綁 job_id + runner;而 operator 服務兩者皆無。偏偏 §1.2/§8.9 最強的安全宣稱(TEE 消除瞬時重建)就靠這條最欠規格的路徑。

修法:新增 §6a 完整規格化一份 grant-scoped 的 0x05 companion(tee_att_op:{grant_id} 記錄、SubmitOperatorTeeAttestation 指令、cbss/operator-tee-attestation/v1 新載荷);全文改為「非復用、落地前 fail-closed、宣稱有條件」,並給了「索性把 tee_required 移出作 follow-up」的替代路。
F5MED撤銷寬限窗可放出「完整」釋放

原文「one last partial」暗示只是單個無害 straggler,實則全部 t 個 proxy 各服務一次陳舊 partial = 撤銷後仍湊齊完整 σ;且長壽金鑰一次釋放即永久洩露。

修法:§3.2 重寫為「窗口內可湊完整 quorum → 完整釋放,鏈只 gate 付款不 gate 重建」;明說疑洩後正解是輪換 K_sign + 撤銷;§1.1 表格與 §8.9 同步。
F6MED限速非鏈上強制,且收緊即 DoS

限速是 proxy 本地/諮詢性、可跨 proxy 子集扇出放大 ~n/t×、且不在計費處;而 §8.9 建議的收緊本身就是對誠實服務的 DoS 槓桿。

修法:§8.9 明確區分軟(proxy 節流)vs 硬(overdraft/delinquency);揭露 DoS-via-tightening → 帳戶級 JobSubmit 全拒;點明限速管成本/騷擾、非金鑰暴露。
F4LOW-MED輪換金鑰對被偷的 K_auth 是 no-op;lockdown 不覆蓋 Grant

version_pin=None 自動跟隨所有未來版本 → 單純輪換秘密擋不住 compromised K_auth(只有撤銷有效);SecretPolicy.actors=Some([]) 緊急鎖定只關 actor 那扇門、不覆蓋 Grant。

修法:§3.1 欄位註解 + §8.9 明寫這兩個腳槍;完整 lockdown 須枚舉 Revoke 所有 Grant。
M1LOW-MEDPrincipal enum 判別式須規範化 + 經認證

原文把 runner/operator 兩 arm 的序列化留到「impl time 和解」。簽名 domain 前綴只擋簽名重放,擋不住共識關鍵路徑上對 arm 的派發歧義。

修法:§3.3 規範:判別式須前導、經認證的 1-byte tag 入 request_hash 原像;domain 字串與驗簽金鑰都從已認證的 in-body arm tag 選,非外層 codec framing。
L1LOWrelease_id 加 principal 域字節(縱深防禦)

keccak256 抗碰撞使今日跨 arm 碰撞不可行(原像 164B vs 124B),但兩構造共用同一去重/quorum 命名空間,值得一個顯式 arm tag 防未來欄寬變更。

修法:§3.3 兩 arm 各加前導 u8(runner 0x00 / operator 0x01)。
被駁倒的攻擊假設(為什麼核心是穩固的)
假設判定理由
跨協議簽名重放駁倒三重分離:domain 前綴不同 + 驗簽金鑰源不同 + 經認證的 arm tag
release_id 碰撞駁倒原像長度與佈局皆異(164B vs 124B),要碰撞需破 keccak256,且含 32B CSPRNG nonce
recipient/MPK 混淆駁倒operator arm 保留 RecipientMismatch 檢查(§3.6 逐位元組相同)
determinism fork駁倒鏈層驗證全讀 current head 且確定;service_label/限速/TTL 皆鏈下,不入共識派生

Gate 判決 needs_human:規格層 + 機密性屬性依鐵律終審歸人;建議先修 F7、更正 F5/F6 措辭,再考慮 lift 進 canonical CIP-24。以上 6 條已全部折入 v2。

⑦一句話總結

這份修正案給 CBSS 開了第三扇門:讓帳戶用一張鏈上憑證 + 一把獨立的暖授權金鑰,授權自己的常駐服務把自己的機密簽名金鑰臨時釋放出來用——不需要 job、不需要 dispatcher、不需要部署 actor,而且完全不動密碼學(因為秘密仍機密,留在同一 IBE 身分空間)。

它把「明文躺硬碟」升級成「可撤銷、門檻保護、有審計」;但誠實地不宣稱消除瞬時重建(那要 TEE,且 TEE 路徑是尚待落地的跨倉依賴)。經 Marshal 兩路對抗審計,密碼學核心判定穩固,6 條「宣稱準確性」發現已全部修入。
