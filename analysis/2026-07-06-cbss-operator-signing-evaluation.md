# Evaluation: What role can CBSS play in the operator signing flow?

**Date:** 2026-07-06
**Scope:** CIP-34 cross-chain chat demo (`node/examples/cip34_chat_demo`) operator/deployer
signing, evaluated against CBSS (CIP-24) capabilities.
**Status:** Evaluation + recommendation. No implementation yet.

---

## 1. Problem statement — how the operator signs today

The demo's operator (a.k.a. deployer) account `0x51F7…` signs **all Cowboy-side
transactions server-side** with a **plaintext secp256k1 key file**:

- Key: `node/.cowboy/key` (65-byte hex secp256k1 private key; generated by
  `start_cowboy.sh` on first run).
- The web server (`server.js`) shells out to the `cowboy` CLI with
  `--private-key $DEPLOYER_KEY` for three transactions:
  1. **chat actor call** — `cowboy actor execute --handler chat …` (submits the user
     message to the on-chain CIP-34 actor), `server.js:390`;
  2. **bridge approve** — `cowboy token approve …`, `server.js:322`;
  3. **bridge withdraw / bCBY burn** — `cowboy actor execute --handler withdraw …`,
     `server.js:343`.
- The `/api/chat` endpoint that triggers signing is defended by loopback-bind +
  per-session token + CSRF (Content-Type/Origin) checks.

**Weaknesses of the status quo:**
- The key is a **single plaintext file at rest** — file/host compromise = full
  operator impersonation, no threshold, no policy gate on the key itself, no
  per-use audit of the key material.
- Signing authority is **all-or-nothing** and **unaudited at the key layer** (only
  the resulting on-chain tx is visible; nothing records "the key was used").

The question: *can CBSS improve this?*

---

## 2. What CBSS actually is (capability map)

CBSS (CIP-24) is a **4-of-5 threshold-IBE _secret release_ service on BLS12-381**.
System actor `CBSS_SYSTEM_ACTOR = 0x04` (`node/types/src/constants.rs:194`).

- **Crypto:** threshold BLS over BLS12-381 (`cbss-crypto`). A partial is
  `σ_i = share_i · hash_to_G1(identity)` (`threshold.rs:18`); Lagrange-at-zero
  combines to `σ = MSK·I ∈ G1` (`threshold.rs:75`). IBE (hashed Boneh–Franklin, v2
  with an encryption ephemeral) wraps an AES-256-GCM DEK; decrypt derives the AEAD
  key from `e(σ,U)` (`ibe.rs:153`).
- **Only exposed product = decryption/unlock _shares_.** The single client RPC is
  `PartialSign` (`cbssd/src/protocol.rs:42`), which returns `σ_i` (a G1 share) for a
  specific on-chain `secret_id`/`version` release request — **never a plaintext and
  never an arbitrary-message signature.** Combine + `ibe_decrypt` happen
  **client-side** (`cbss-client/src/combiner.rs:55`); the plaintext secret is
  reconstructed **on the requesting client**, transiently.
- **Committee:** n = 5, t = 4 (`node/execution/src/cbss.rs:28`); group key via DKG
  (Pedersen/VSS or vetted commonware DKG); re-share/churn supported
  (`RequestReshare`/`RotateCommittee`).
- **Release is heavily gated on-chain** (`cbssd/src/chain_authorizer.rs:82`): https/
  loopback, runner secp256k1 signature, chain-metadata match, request freshness
  (≤ 384 blocks), **policy ACL (`policy.actors` allowlist)**, **job binding
  (callback actor == request actor AND runner assigned to the job)**, **actor
  manifest `secrets.read` entitlement covering `(account,key)`**, optional TEE
  attestation, and proxy-in-committee. Every release is **accounted on-chain**
  (`SubmitReleaseReceipt`, `cbss.rs:1199`) with slashing evidence.
- **tlock** (`RegisterTlockRelease`/`SubmitTlockRelease`, opcodes 152/153) is the
  same machine keyed on `hash_to_G1(tag ‖ target_height)` — effectively
  **threshold-BLS signing of an arbitrary `tag`, gated by a height**.

### The load-bearing constraint

- **CBSS has no arbitrary-message signing API, and NO secp256k1 / ECDSA
  threshold-MPC signing anywhere** (grep for FROST/GG18/GG20/threshold-ECDSA across
  `cbss/`, `node/execution`, `node/types`, `runner/` returns nothing). All
  secp256k1 use is **single-key** ECDSA for identity/authorization only.
- Cowboy transactions are **secp256k1**. CBSS's threshold is **BLS**.
  → **CBSS cannot co-sign an operator transaction.** It is a *secret-release*
  service, not a *signer*.

Therefore CBSS can only participate in operator signing at the **key-custody /
release / authorization** layer — never as the signature producer.

## 3. Integration models

| # | Model | How | Gain | Limitation |
|---|-------|-----|------|------------|
| **A** | **CBSS-custodied operator key (envelope / threshold-KMS)** — *recommended* | Store `.cowboy/key` as a CBSS secret (IBE-encrypt, `SetSecret` + `SecretPolicy`). ### 3.1 Transient reconstruction is inherent — only a TEE removes it

CBSS is a *release* service, not a signer and not a "use the key on your behalf"
enclave. Its threshold produces a decryption element `σ = MSK·I`; the **client**
then derives the AEAD key and `ibe_decrypt`s the wrapped secret **in its own
memory**. So the plaintext secret always exists, transiently, in the requesting
client at the moment of use. This is true for **every** secret CBSS releases:

- the **operator key** → reconstructed in the **demo server**'s memory before it
  signs;
- a **job secret** (LLM/EVM key) → reconstructed in the **runner**'s memory before
  it calls the API.

**Custodying the LLM key does *not* avoid transient reconstruction** — the mechanism
is identical. What differs between the two is *not* the transient exposure but
(a) **blast radius** — a reconstructed operator key can sign arbitrary on-chain
authority (mint/burn/transfer), a reconstructed LLM key can only spend an external
API budget; (b) **where** it is reconstructed — the runner is the *intended*
reconstruction point for a job secret, a web-facing server is not; and (c)
**integration effort** (see §4).

The only ways to remove the transient plaintext at the client:

1. **TEE** — perform the reconstruction inside an enclave. CBSS supports gating a
   release on `policy.tee_required` (a live, unrevoked, in-window TEE attestation,
   `chain_authorizer.rs:194`), so the decrypted plaintext lives only inside the
   enclave and the host never sees it. **Applies equally to the operator key and job
   secrets**; the runner already has the TEE-attestation plumbing, so it is more
   readily available there.
2. **Threshold "in-use" computation** (the key is never reconstructed at all) —
   threshold signing / threshold decrypt-and-use. CBSS does **not** provide this
   (no secp256k1 TSS; its threshold BLS still yields a client-combined `σ`). This is
   the Model-D / CIP-level direction.

Net: CBSS removes the **at-rest** plaintext (the key no longer sits in a file) and
adds threshold custody + policy + audit. It does **not** remove the **in-use**
plaintext exposure unless layered with a **TEE** — and that limitation is the same
whether the custodied secret is the operator key or a job secret.

## 4. Integration friction (important)

CBSS's authorizer is **job/actor/runner-centric**: a partial is released only when a
**runner assigned to a job**, for an **actor holding a `secrets.read` entitlement**,
asks for a secret bound to that `(account,key)` (`chain_authorizer.rs:144`, `:165`).
This shape is designed for **provisioning a runner with a job secret** (e.g. an LLM
API key for an LLM job), *not* for custodying a server's own operator signing key.

An operator-signing server is **not executing a job**, so the job-binding and
manifest-entitlement gates don't apply as written. To adopt Model A you must pick
one of:

- **(a) New "operator principal" release class** — extend `cbssd`'s authorizer +
  add a `SecretPolicy` variant that authorizes a **registered operator identity**
  (a secp256k1 principal on an allowlist, with freshness + optional TEE) rather than
  a job-bound runner. Clean, but touches the authorizer and a new policy path.
- **(b) Frame signing as a job** — model each signing operation as an actor job so
  the existing gates apply. Awkward: signing is the server's action, not an actor's
  job, and it inverts the control flow.

Recommendation: **(a)**, gated behind an explicit opt-in, if operator-key custody is
pursued.

### A more natural first landing

CBSS is a **much better fit for the secrets the runner already uses for jobs** —
the demo's **LLM (GLM) API key** and **EVM demo key**, which today live in plaintext
`env/*.secret.env`. Those are exactly the "provision a runner with a job secret"
shape CBSS was built for (`runner-http`/`runner-agent` executors already accept an
optional `SecretsClient` and substitute released bytes — `runner-agent/src/executor.rs:272`
is still a `TODO(secrets)` stub). Landing CBSS there first proves the end-to-end
release path in the demo with **no authorizer changes**, before deciding whether the
operator key warrants the new operator-principal path.

To be explicit: this "better fit" is about **integration effort and blast radius**
(§3.1), **not** about avoiding transient reconstruction — a released LLM key is still
reconstructed in the runner's memory at use time, exactly like the operator key in
the server. Removing that in-use exposure needs a **TEE**, for either secret.

---

## 5. Recommendation

1. **If the goal is specifically the operator signing key:** adopt **Model A**
   (CBSS-custodied operator key) behind an explicit opt-in, with the **operator-
   principal release class (§4a)**. State the honest limit: the key is transiently
   reconstructed in memory at sign time; this is a threshold-KMS + policy + audit
   improvement over a plaintext file, **not** threshold signing.
2. **Do not** attempt "true threshold signing" (Model D) for the demo — it needs a
   secp256k1 TSS (absent) or a new on-chain BLS authorization path. Track it as a
   CIP-level future.
3. **Pragmatic sequencing:** land CBSS first on the **LLM/EVM job secrets** (the
   native fit, no authorizer change) to prove the release path end-to-end in the
   demo; then evaluate whether the operator key merits the operator-principal work.

## 6. Open questions

- Does the demo want the **operator key** protected, or is provisioning **job
  secrets** (LLM/EVM) the actual intent? These have very different effort.
- Committee/DKG operational cost in the demo: CBSS needs ≥ 5 staked, registered
  proxies + a DKG ceremony. Is that acceptable demo setup, or should the demo run a
  reduced (e.g. t-of-n with small n) committee?
- Is a transient in-memory key reconstruction (Model A) an acceptable trust story
  for the demo's narrative, or is the "operator signs server-side" honesty label
  (already in the UI) sufficient without CBSS?
