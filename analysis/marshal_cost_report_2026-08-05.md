## 四、为什么 07-26/27 起 token 陡增,而份数没涨?(核心发现)

**一句话:是「每份审计变深(轮数翻 2–4 倍)」,不是「审得更多」,也不是「上下文变胖」。**

对比三个实测指标(取每日中位数):

| 时期 | 基线静态上下文 | 轮/会话 | cache-read/轮 | token/份 |
|---|---:|---:|---:|---:|
| 分水岭前(07-20) | 17K | **20** | 74K | **2.7M** |
| 分水岭前(07-24) | 40K | **17** | 80K | **2.1M** |
| 分水岭后(07-27) | 18K | **78** | 149K | **9.5M** |
| 分水岭后(07-30) | 29K | **57** | 149K | **12.6M** |

三条证据链:

1. **不是静态上下文膨胀**。「基线静态上下文」= 会话头几轮的最小 cache-read,代表系统提示 + CLAUDE.md + 记忆 + 工具的固定大小。它全程稳定在 **17–41K,没涨**,07-27 反而更低。→ 排除「MEMORY.md / CLAUDE.md 变大」。

2. **不是份数增长**。07-20 有 15 份、07-27 有 29 份,但 token/份 从 2.7M 飙到 9.5M。份数只翻倍,token/份翻 3–4 倍。

3. **真因 = 每份审计的轮数从 ~15–20 暴涨到 ~45–78(2–4×)**。轮数一多,**每轮都要重读整段累积的会话历史**,所以 cache-read/轮 也从 ~74K 涨到 ~149K(第 60 轮要重读前 59 轮的全部)。

**两者相乘 = 超线性**:轮数 ~2.5× × 每轮上下文 ~2× ≈ 每份 token ~4–6×。这就是曲线陡起的数学原因。

**为什么轮数陡增 —— 待审 PR 的性质变了。** 7 月中下旬前队列多是浅 PR(docs/examples 清理、简单改动),几轮审完;**从 07-26/27 起队列被深共识面 PR 填满**,每个都要大量 scout / prove / 跨仓 grep / 变异推理 / 多视角对抗验证:

- **CBQS #290**(前后 24 轮 escalate)、cp#67/68 / cowboy#294/295 计价单位族
- **PVM lockdown 系列**(#1227/1228/1235/1237/1224/1232 …… RCE / 网络 / 文件 / sys 泄漏,每个都要读 pvm 源码 + 跨仓确认)
- **tx-contract slice**(#1244/1245/1246/1249,per-tx overlay + golden 差分)
- **eth-LC bridge #1200**(r5→r8,读 2500 行 diff + BLS / gindex 归因)
- **runner 盲签栈**(#200–205,多轮 nonce-recovery)

这些每份天然 40–80 轮,而一个 examples 清理可能 10 轮就结。

> **可操作结论**:深审 / 多轮 PR 的单份成本是**超线性**的——每多一轮都按 cache-read 价重读整段会话。若要控成本,杠杆在「**缩短单份会话轮数**」(如更早分诊、限制无谓 scout 轮次),而不是「少审几个 PR」。

## 五、口径修正说明

本报告修正了初版估算的两处高估 + 一处低估:

1. **streaming 双计(~2×)**:transcript 对每条 assistant message 的 `usage` 记 partial+final 两次。按 message id 去重消除。→ 月度总额从初版 **$10,654 修正为 $5,142**。

2. **审计份数膨胀(~3.3×)**:`gate-record --change-ref` 文本在 transcript 出现约 3.3 次/次(streaming + tool_result 回显 + 小结引用)。去重后真实审计动作 = **345**(初版误报 1137)。

3. **同一 PR 的多轮深审 —— 已正确分别计数**:作者每 push 一次 head sha 变化,每轮 re-review(如 #1200 的 r5→r8、runner#202 三轮)都是**不同 change-ref sha**,各记一次。经核:唯一 head = 344,审计动作 = 345,**每 head 平均被审 1.00 次**(marker 机制阻止同 head 重审;多轮审计体现为多个 head)。一个多轮 PR 的真实成本 = 轮数 × 单份成本(例:#1200 审 4 轮 ≈ $60)。

**净效果**:总额被高估 2×(→ $5.1k);每份审计反而被**低估**($9.4 → $14.9),因份数比总额膨胀更狠,两错相除把单价压低了。

## 六、重要口径:API 等值 ≠ 实际支出

- 本机为 **OAuth 订阅登录(Claude Max)**,非 API key 按量计费(配置无 `apiKeyHelper`,存在 `~/.claude/.credentials.json`)。
- 报告中所有金额是「**假如走 API 单价会折合多少**」的**参考等值**,**不是真实账单**。订阅为每月固定费,per-token 未被计费。
- 因此 `/usage` 显示的成本远小于本报告 —— 那是订阅额度内的真实口径,**是对的**;本报告用于评估「这套自动化相当于多少 API 价值 / ROI」。

### 计价档说明
- **标准档**(主口径,≤200K 上下文):input $15/M、output $75/M、1h cache-write $30/M、cache-read $1.5/M。

## 七、常见困惑(FAQ)

**Q:为什么这份报告 $5.1k,而 `/usage` 显示小得多?**
A:计费模式不同。你是**订阅**(固定月费),per-token 没被扣;本报告是「折合 API 单价」的假想值。`/usage` 是真实账单口径,它小是对的。

**Q:为什么审计份数(345)比巡检轮数(442)还少?**
A:很多轮**队列为空**(没 PR 需审 / 都已在当前 head 审过)。空轮仍跑 `find_targets` + 小结,有小额成本但 0 份。

**Q:「每份 $14.90」和明细里 07-27 的「9.5M token/份」对不上?**
A:$14.90 是**全期平均**,掩盖了巨大方差:早期浅 PR ~$5/份,深审高峰 ~$25–30/份。看单日更准(见 §3、§4)。

**Q:cache-read 占 97% token 却只占 60% 成本,矛盾吗?**
A:不矛盾。cache-read 单价最低($1.5/M),output 贵 50 倍($75/M)。token 量和花的钱是两个维度(见 §2)。

**Q:一个 PR 审了好几轮,成本算重了吗?**
A:没算重也没漏。每轮在**不同 head**,各是一次独立审计(各烧 token),已分别计入 345 份。多轮 PR 的总成本 = 轮数累加(见 §5.3)。

**Q:「每份成本」是纯一个 PR 的开销吗?**
A:不是。一轮 sweep 审 2–3 个 PR 并共享 find_targets / 小结开销,「每份」= 整轮 ÷ 份数,已把共享开销摊入(见 §1 注)。
