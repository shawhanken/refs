## 一、CLI 与 SDK 开发优先级

- **SDK 是最核心的前置依赖**：`cowboy init`（脚手架）需要调 SDK，AI Context 模块也需要等 SDK 完成，因此 SDK 优先级最高。
- **其他 CLI 命令（除 `cowboy init` 外）** 大部分估计只需一两天工作量。
- **`cowboy actor logs`** 需要内部几位开发对齐 PVM 日志输出和存储方式后才能推进。
- **本地调试功能已暂时剔除**，不向客户承诺近期交付。

---

## 二、SDK 开发的现状与挑战

1. **PVM 尚未定型**：说话人3 正在将 PVM 合并进 GitHub 的 NODE 仓库（从子模块改为直接合并），因为客户方觉得子模块方式操作不便，且之前的子模块脚手架工具已被删除。
2. **FSM（状态机）尚未实现**：在状态机未实现前做 SDK 属于"冒进"，SDK 里的装饰器（decorator）在当前阶段本质上是**伪实现**——语义层面存在，但底层不会真正执行。
3. **SDK 装饰器数量多**：参照 CIP-6 文档，大约有14-15个装饰器需要逐一实现和测试，预估至少需要 **1-2周** 时间。
4. **AI 编程的局限性**：团队反思 AI 编程虽然效率高、改代码快，但出错率很高，死代码多，测试环节仍然耗时，尤其是涉及签名、状态、接口等底层逻辑时，AI 无法真正替代人工。

## 五、DevEx（开发者体验）产品化讨论

### 客户核心需求场景
- 会技术的用户通过 CLI 部署 actor
- 不会技术的用户通过 CowChat（自然语言）部署 actor
- 能够观察和感受 **deferred transaction**（延迟交易）的过程

### 当前系统能力
- 用户**已经可以**自己用 Python 写 actor 并部署到链上，完全可以运行
- 只是语法较原始，没有 SDK 封装，代码可读性/语义化不够友好
- 缺少调试工具（Runner 状态、链日志、actor 状态等对外不可见）

### DevEx 缺乏产品设计
- 客户方**没有**给出 DevEx 的具体产品设计方案/原型
- 只有粗略方向描述（能部署、能调试），不是可执行的产品规划
- 说话人1 决定：**主动从 Slack 中分析客户对 DevEx 的设想**，生成一个步骤流程，然后拿着这个与客户确认

### DevEx 的数据来源
- 主要数据（actor 状态、transaction 进度等）都在链上，通过 RPC / indexer 获取
- DevEx 本质上可以是一个独立运行在浏览器里的工具
- 不需要 NODE 或 PVM 提供直连接口，但基础设施持续变化会导致 DevEx 频繁失效

## 六、签名方案问题（ED25519 vs secp256k1）

- 当前系统使用 **ED25519**，但客户白皮书要求与 **EVM 兼容**（EVM 用 secp256k1）。
- 如果全面改回 secp256k1，**三个系统（NODE、PVM、Runner）都需要大改**，所有接口和存储架构都有变动，代码几乎全部要翻一遍。
- 即使用 AI 辅助，**一周都挡不住**，且测试工作量巨大。
- **应对策略**：
  - 向客户说明 ED25519 的优势
  - 提出折中方案：未来 EVM 接入时，外层套一个壳做地址的**一对一映射转译**，兼容20位地址
  - 先沟通清楚，让客户做决策

---

## 七、Token（CIP-20）相关

- 客户要求将 CIP-20（Fungible Token Standard）优先级提前。
- Token 发行是 DevEx 的配套需求（吸引开发者需要空投 Token）。
- 实现方式参考 Solana 的 SPL（Solana Program Library）思路，通过系统 actor 实现。
- 但 Token 与 EVM 兼容之间也有差异，可能需要隔一层来做映射。
- 目前**尚无定论**，暂时可以不急。
