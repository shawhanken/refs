04

Why tokens spiked while audits didn't

It's "each audit got deeper (rounds up 2–4×)," not "more audits," and not "a bigger context." Three measured metrics make it clear:

PeriodBaseline static ctxRounds/sessionTokens/audit
07-20 · before17K202.7M
07-24 · before40K172.1M
07-27 · after18K789.5M
07-30 · after29K5712.6M

Three lines of evidence:

① Not context bloat. Baseline static context (system prompt + CLAUDE.md + memory + tools) stays steady at 17–41K, no growth, and is even lower on 07-27.

② Not more audits. Audits merely doubled; tokens/audit tripled–quadrupled.

③ Real cause = rounds/audit 15–20 → 45–78. More rounds means each round re-reads the whole accumulated session, so cache-read/round rose 74K → 149K (round 60 re-reads rounds 1–59).

Super-linear: rounds ~2.5× × per-round context ~2× ≈ tokens/audit ~4–6×

Why rounds spiked — the PR mix changed. Before mid/late July the queue was mostly shallow PRs (docs/examples cleanup); from 07-26/27 it filled with deep, consensus-critical PRs, each demanding heavy scout / prove / cross-repo grep / mutation reasoning / multi-lens adversarial verification:

  • CBQS #290 (24 rounds of escalate over its life), denomination cluster cp#67/68 · cowboy#294/295
  • PVM lockdown series (#1227/1228/1235/1237/1224/1232 — reading pvm source + cross-repo confirmation)
  • tx-contract slice (#1244/1245/1246/1249, overlay + golden diffs)
  • eth-LC bridge #1200 (r5→r8, 2500-line diff + BLS/gindex attribution) · runner blind-sign stack (#200–205, multi-round)
Actionable: per-audit cost of deep/multi-round PRs is super-linear — every extra round re-reads the whole session at cache-read rate. The cost lever is "shorten rounds per audit" (triage earlier, cap pointless scout), not "review fewer PRs."
05

Accounting corrections

The first pass stacked two overestimates + one underestimate. After the fix: total halves, per-audit goes up.

Over · streaming double-count

$10,654→$5,142

Each message's usage is logged twice (partial + final, ~2×). Deduped by message id.

Over · audit-count inflation

1,137→345

gate-record text appears ~3.3× per call (streaming + tool_result echo + summary refs).

Already right · multi-round

1.00×

Each push changes head → every re-review is a distinct sha, counted once. Multi-round PRs sum over rounds (#1200's 4 rounds ≈ $60).

Net: total overstated 2× (→ $5.1k); per-audit was in fact underestimated ($9.4 → $14.9) — the audit count was inflated more than the cost, dividing to a too-low unit price.

06

FAQ

QWhy $5.1k here but /usage shows far less?

Different billing. You're on a subscription (flat monthly fee); nothing charged per token. This is a hypothetical "folded to API prices." /usage is the real bill — small is correct.

QWhy fewer audits (345) than runs (442)?

Many runs had an empty queue (nothing to review / all at current head). Empty runs still run find_targets + a summary — small cost, 0 audits.

Q"$14.9/audit" vs 9.5M/audit in the table?

$14.9 is a whole-period average hiding variance: shallow early PRs ~$5, deep peaks ~$25–30. The daily view is more precise (03, 04).

Qcache-read 97% tokens yet 60% cost — contradiction?

No. cache-read has the lowest unit price ($1.5/M); output is 50× ($75/M). Token volume and dollars are two axes (02).

QA PR reviewed many times — double-counted?

Neither. Each round is at a different head, an independent audit (each burns tokens), counted separately in the 345. Total = sum over rounds.

QIs "per-audit cost" one isolated PR?

No. One run reviews 2–3 PRs sharing find_targets/summary; "per audit" = whole-run ÷ audits, shared overhead amortized in (01).

07

Key caveat · API-equivalent ≠ actual spend

KeyThis is subscription billing, not per-token

This machine runs on OAuth subscription login (Claude Max), not a metered API key (config has no apiKeyHelper; ~/.claude/.credentials.json is present).

Every dollar figure is a reference equivalent — "what it would fold to at API unit prices" — not a real bill. The subscription is a flat monthly fee; nothing was charged per token. That is why /usage shows a cost far below this report — that is the real, in-subscription figure and it is correct. This report gauges "how much API value / ROI this automation represents."

What does "1M premium ceiling" mean? The model is Opus's million-token long-context variant (claude-opus-4-8[1m]). Anthropic bills any single request whose context exceeds 200K at roughly 2×. So the same usage folds into two prices: $5,142 = assume all requests at standard rate (lower bound); $10,300 = assume every request lands in the premium tier (upper bound, essentially never fully hit). The real value sits between, closer to $5.1k — only the deep multi-round sessions that pass 200K pay the premium. It's a range $5.1k–$10.3k; the "ceiling" is a cap, not a second real number.

Bottom line — one PR deep review ≈ 6.1M tokens / ~$15 API-equivalent (cache-read is 60% of cost); over the past month, 442 cron runs and 345 audits ≈ $5.1k API-equivalent (range $5.1k–$10.3k). Per-audit cost rises super-linearly with review depth (rounds) — after the queue turned to deep consensus PRs in late July, each audit jumped 4–6×. Under subscription billing none of it is real spend; /usage is the actual figure.
