继续讲一下目前遇到的障碍和困难，让大家能够理解一下。
我先说一下相关困难。我们这边在推进过程中一直有沟通：有很多 issue 下发之后，其实跟我们之前用 AI 扫一遍得到的结论不一样。真正做下去的时候会发现不是那么回事，或者没那么简单；也可能是 issue 和 issue 之间、issue 和 CIP 之间起了冲突，没法解决。大量遇到这样的问题。
具体描述的话，看老王或者老严这边能不能举个例子，让太一这边更有场景地理解一下。
我来说一下我这边遇到的情况。
首先讲一下进度。基本上每天还是维持差不多十个左右 issue 的修复速度。目前还剩余一百多个。8 月 20 号这个时间确实蛮紧，所以每天尽可能要保证这个速度，当然我们希望更快，最好一两周就能搞定。这是第一个大的情况。
实际遇到的问题是：有一部分 issue，修到一定阶段以后，会发现问题。开始的时候，issue 会先做评估：这个 issue 值不值得做、这个 issue 会有什么问题。即便 AI 在初期做 issue 说明的时候认为可以做，真正做了以后，到后来也有一定概率发现修不下去。
所谓冲突，主要是和已有的 CIP 或已有设计之间存在比较严重的冲突，导致不能再继续做下去。最近这种情况越来越多。
我的感觉是，先不定量判断问题到底发生在哪里，先定性判断有没有这种可能性：我们解到一定程度以后，就像解方程组一样，三个方程解三个未知量一般可以解；但现在可能是四个方程、五个方程去解三个未知量。你在三个方程里面解出来是正解，但放到另外几个方程里又不是同一个解释。
现象非常典型：按照某个 issue 或某个标准看，AI 都能修，也都能背书，似乎没问题，可以马上修；但修完以后，会发现它和另外一些地方产生了冲突。
用更严格一点的数学语言描述，这已经有点像“过定约束”的状态。CIP 里面有大量定义、描述或者重复描述，中间应该存在过度定义的问题。显性的两个描述之间可能有显性冲突，隐性之间也可能冲突，或者是过度定义导致的问题。
举个例子，在修复过程中，工具主要参考某一个 CIP A 的要求，就会按这种结论去修复；但从另一个角度看，另一个 issue 可能参考 CIP B，同样也有类似概念，可能会得出另一个修复方向。所以这个过程中一直在产生冲突。这是我的感受。
所以从前天凌晨到今天，我事实上一直在对这些 CIP 做进一步处理，看里面有没有可能存在过度定义的情况。我发现这比找 CIP 里面不一致要难得多。CIP 不一致比较好找，描述上有差异是好找的。现在更像是每个描述大概都对，在它自己的 CIP 角度可能都没问题，但是放到一个宏观的大结构里，有几十个 CIP 共同约束，再加上完整研发过程，就可能在深层次产生问题。
浅层的问题我们都排查了。修某一个 issue 的时候，如果有问题通常能排出来，但现在是修了几轮以后才发现走不下去。以前没有这种情况，但从上周开始已经出现了。甚至有几个 PR 最后只能不得不 close，不是因为解决问题以后 merge close，而是只能 close，因为已经做不下去了。进去七八轮之后才发现问题。
未来剩下的这些 issue 当中，不知道还会不会有这样的问题。所以我现在的对策是：
第一，对 CIP 进行排查。
第二，对于这些 issue，我正在设计或者构思一个工具：能不能在 issue 修复之前，用某种方式先触发检查，判断它修复的核心本身是不是会引发什么问题。最好能够把这些问题归纳出来。
举个例子，如果能一开始就找到这些 CIP 当中存在的问题，经过一系列计算以后，我们就可以马上提出来，跟官方进行沟通复审，避免修了很久，花三四个小时不停修，到最后才发现整个体系推进不下去。这个损耗太大。
这是我这边遇到的一些问题。对策上，我也在想增强工具能力。现在这个工具虽然一开始有自动化检测，检查每个 issue 修复的正确性，但好像没有查出这类问题。以至于修复过程中已经发生了两个 issue，是进行了十几轮修复以后，才发现修不下去。我人工花了很长时间去审，开始也没看出问题，直到十几轮以后才暴露出很多冲突。现在只能人为给这些 issue 做标记，在列表里面加标记。
我大概已经懂了。你能不能写文档？因为我刚才讲的，issue 不是这么回事。
好的，是个问题。我想找到它产生的最根本原因是什么。我需要有一个文档。
我其实遇到的问题和老严那边也类似。很多时候，有不少 issue 看起来可能很简单，但真修起来的时候并不是表面看起来的东西。基本上我修一个 issue，可能会蹦出来三四个 follow-up，还得新建三四个其他 issue，再配套去解决问题。所以目前看来，现在遗留的那些 issue，每个修起来都挺费劲。
我想的是跟官方沟通一下，看哪些 CIP 的优先级可以降低。比如有些东西可能还没有完全想完。
核心还是说，我们把核心写一下，确定优先级。那些定义不清楚的 issue，就直接拿出来讨论。已经没办法直接修了。因为这些 issue 生成的时候，生成 issue 的模型不一定明白是什么事；而且当时用的模型版本或者能力也有可能有问题。
刚刚这一点特别好。明天开会的时候，能不能针对这些 issue 做一个小结。我大概抽象一下：
第一，一个 issue 表面上是一个 issue，其实背后是多个 issue。
第二，这个 issue 中间可能有 60% 需要实现，另外 40% 的内容是否需要实现并不清楚，因为有很多方式会包含一些不大的功能点。
第三，issue 和 issue 之间可能会冲突。这个 issue 要这样改，另一个 issue 因为生成的时候没有把所有相关 issue 都看一遍，所以可能会生成一个 overlapped 的 issue。
那就看能不能做一个 document 出来，最好是有实例。每类问题举一个例子。
