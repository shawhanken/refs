## 1. 范围与摘要

本文回答三个问题：

1. Hyperliquid 由哪些组件构成？
2. 每个组件可以由哪个 Cowboy 组件承接？
3. 哪些部分 Cowboy 完全无法提供？

**方法。** 将 Hyperliquid 拆解为十九个组件（§2），并为每个组件标注它所依赖的平台性质 ——
决定是否存在替代方案的是这个性质，而不是组件的功能。随后把每个组件映射到具名的 Cowboy 组件
及其对应 CIP（§4）。缺口附出处与严重程度（§6）；整套架构所倚赖的那一个定量问题以计算得出，
而非估计（§9）。

### 结论摘要

**有一条前提无法移植，其余一切由此推出。** Hyperliquid 的决定性设计是把共识做得足够快，
使订单簿能够存在于共识之内 —— 每一笔下单、撤单与成交都是一笔交易。Cowboy 的出块时间与吞吐距离
支撑这一点相差三个数量级（§3），且没有任何 roadmap 项目能补上。正确的应对是不去尝试。

**Hyperliquid 的其余部分映射干净。** 将撮合下沉到链下 Runner、订单级数据放入 CBFS、
订单流走 CBQS，而结算、托管与治理保留在链上之后，十九个组件中有十六个今天就有归属或有具名的
建设路径（§4）。由此得到的系统在 CBFS、CBQS、CBSS、Runners 与 PVM 之间均衡分布，
PVM 承担托管而非热路径。

**三个缺口是承重的**（§6）：

| 缺口 | 严重程度 | 后果 |
|---|---|---|
| 没有常驻 Runner 服务（CIP-10 §16.2） | **阻塞** | 撮合引擎按定义即为常驻服务，而容器运行时是临时的。它挡住的是每一个常在线服务，不止本用例 |
| 没有协议层价格 oracle（CIP-2 v3） | **对永续合约阻塞** | mark price 与资金费按作业往返到达，而非按块。现货不受影响 |
| Sequencer 公平性是信任假设 | **需如实披露** | 订单优先级由有 bond 的运营方主张，而非由共识证明。这是本设计在结构上唯一弱于 Hyperliquid 之处 |

**结算并不是通常以为的那个约束。** 以 gas 模型而非交易速率来计算，每块结算可支撑
884–7,386 fills/sec（取决于编码方式），比一个大型场所的实际成交量高出一到两个数量级。
结算窗口应取一个块，这个参数需要的是默认值而非调优（§9）。最终化时间由争议窗口主导，
而非由结算窗口主导。

## 2. Hyperliquid 拆解

六组共十九个组件。最右一栏是关键：它点出该组件**所依赖的性质**，
这决定了 Cowboy 的组件能否替代它。

> Hyperliquid 的细节取自公开文档，应按「结构准确、数量级准确」理解，而非钉死的数值。
> 下文没有任何结论依赖某个具体数字；§3 是一个三数量级的论证，即使错一个数量级仍然成立。

### 2.1 共识与执行

| # | 组件 | 功能 | 依赖 |
|---|-----|------|------|
| 1 | **HyperBFT** | HotStuff 衍生的 BFT 共识，以 Rust 为订单流专门构建。公开数据为亚秒级最终性与约 10⁵ orders/sec。 | 共识本身快到足以充当撮合引擎的 sequencer |
| 2 | **HyperCore** | 状态机：永续与现货、订单簿、保证金、清算、资金费。每一笔下单、撤单与成交**即是一笔交易**。 | #1。没有它该设计不成立 |
| 3 | **HyperEVM** | 共用同一套共识的通用 EVM 执行层。双区块（小/快、大/慢）。经 precompile 读 Core，经 CoreWriter 写 Core。 | 与 #2 共用共识，使 Core 状态可同步读取 |

## 3. 无法移植的那条架构前提

组件 #1 与 #2 实为同一个设计决定：*把共识做得足够快，使订单簿能够存在于其中*。
Hyperliquid 一切独特之处皆由此派生。这也是 Cowboy 唯一无法复现的性质，
而且该差距是结构性的，不是调参问题。

| | Hyperliquid | Cowboy |
|---|---|---|
| 出块 / slot 时间 | 亚秒级，专门构建 | **约 1 s**（WP-v2 §6.1 / §13；CIP-11 r1.2 与 CIP-23 r1 均按此校准） |
| 工作单位 | 一笔下单、撤单或成交 = 一笔交易 | 一次 actor 调用 ≈ 50k cycles |
| 实测吞吐 | 约 10⁵ orders/sec（公开宣称） | **实测 50–150 TPS，理论上限约 500 TPS**；devnet 基准峰值 457 tx/block（2026-03-31） |
| 完成全部吞吐 roadmap 之后 | — | 1,000–3,000 TPS，取决于冲突率 |

相差三个数量级，而 roadmap 自身的最好情况尚不足以补上其中一个。因此，
复现 HyperCore 的链上撮合在构造上即不在范围内，而非出于偏好。

由此得出 §5 的架构：撮合下沉到链下 Runner，订单级数据进入 CBFS，订单流走 CBQS，
链上保留真正需要共识的部分 —— 所有权、费率表，以及变更它们的权限。

## 4. 组件映射

三种判定。**Have** = 今天在规格层面已有 Cowboy 组件覆盖；**Buildable** = 可落到既有组件上，
但存在真实且已具名的工作量；**No home** = 见 §6。

### 4.1 Have

| Hyperliquid 组件 | Cowboy 组件 | CIP | 说明 |
|---|---|---|---|
| #4 撮合引擎 | **Runner** 工作负载，链下 | CIP-2 | 不由 PVM 承载。常驻约束见 §6.1 |
| #19 L4 / 历史数据 | **CBFS** volume，纠删码，`manifest_root` 上链 | CIP-9 (v2.r2)、CIP-31 | 只追加的行情数据接近 CBFS 的最佳场景 |
| 订单流入、成交流出 | **CBQS** stream，每市场一条 lane | CIP-39 v2 | 有序、at-least-once、可重放 —— 正是订单录入总线的形状。注意事项见 §6.4 与 §6.5 |
| #14 API / WebSocket | **CBQS** 推送投递，加 `GET_STATE` 可验证读 | CIP-39、CIP-17 | CIP-17 使前端可对 `state_root` 验证余额，而非信任单个 Runner |
| #9 HLP、#10 vaults | **PVM actor** | CIP-20 | 托管、份额记账与 PnL 分配 —— 低频、高价值。这是 PVM 的正确角色 |
| #7 资金费结算 | **CIP-5 timer**，按固定高度节奏 | CIP-5 | 高度触发、显式 `fee_payer`、自终止，无 keeper 依赖 |
| #6 清算反应 | **CIP-29 event hooks** | CIP-29 | CIP-29 的首要用例即 pre-liquidation：订阅者在清算执行前获得同一笔交易内的同步反应窗口。强于其他平台的等效机制 |
| #15 builder codes | `0x09` 的 `SettlementConfig` 分费，或 PaymentGate | CIP-3、CIP-18 | `UpdateSettlementConfig` 已带 `target_pool` 判别式 |
| #18 质押、委托 | 验证者质押加 Runner 委托 | CIP-13 | `effective_stake = registration.stake + delegation_totals.total_active` |
| 交易所侧密钥 | **CBSS** | CIP-24 | 签名密钥与第三方凭证在作业时 t-of-n 释放。明文既不上链亦不暴露给验证者 |
| 撮合器完整性证明 | **CIP-23** composite attestation | CIP-23 | 可选；对撮合器信任问题的实质性回应，边界见 §6.3 |

由此得到的分配使 CBFS、CBQS、CBSS、Runners 与 PVM 处于同等地位，PVM 承担托管而非热路径。

### 4.2 Buildable，工作量已具名

| Hyperliquid 组件 | Cowboy 组件 | 所需工作 |
|---|---|---|
| #5 保证金引擎 | 拆分：热保证金检查在 Runner，已结算保证金状态在 actor | 净额设计 —— 链观察的是每个结算窗口的仓位增量，而非每笔成交。尺寸见 §9 |
| #2 HyperCore 结算状态 | actor 状态加 CIP-20 余额 | CIP-20 提供 `u128` 金额的现货同质代币。永续仓位、杠杆与维持保证金均为应用层 actor 代码，无原生原语 |
| #13 HIP-3 builder 市场 | 仿 Runner Registry 的 actor 注册表 | 质押公式与罚没条件。`max(10,000 CBY, 1.5 × declared_max_job_value)` 是可用模板 |
| #11 HIP-1 ticker 拍卖 | actor | 原属 CIP-22 范围 —— 见 §7 |
| #12 HIP-2 自动流动性 | actor 加 CIP-5 timer | 原属 CIP-21 范围 —— 见 §7 |
| #17 USDC 桥 | CIP-25 L1 锚定 → L2 消息 → L3 桥 | CIP-25 规定了带可插拔信任后端的三层架构；尚无后端部署 |
| #3 HyperEVM | 不适用 | Cowboy 的通用执行层即 PVM。不存在第二套执行环境需要调和，这消除了 precompile 与 CoreWriter 所要解决的一整类 Core 与 EVM 同步问题。属简化而非缺口 |

### 4.3 今天无处安放

组件 #1 与 #8，以及 #4 所依赖的常驻性质。见 §6。

## 6. 能力缺口

按阻塞程度排序，每条附出处。

### 6.1 没有常驻 Runner 服务 —— **阻塞**

> **Long-running services**: v1 containers are ephemeral (bounded by `max_duration_sec`).
> Persistent services (web servers, databases) that run indefinitely are a future CIP.
> CIP-5 timers can be used to re-dispatch periodic jobs.
> —— CIP-10 §16.2，Explicitly Out of Scope

撮合引擎按定义即为常驻服务：它把订单簿保存在内存中，必须持续在线。
CIP-2 / CIP-10 的工作单位是一个有界作业，完成即拆除。规格建议的缓解手段 —— 用 timer 重新派发 ——
在此不适用，因为交易所无法在每个派发周期从 CBFS 重建订单簿。

CIP-39 的 Background 一节将 Runner 描述为在共识之外执行「任务与常驻工作负载」。
这与 CIP-10 §16.2 不一致，而与已交付的容器运行时相符的是 CIP-10 的表述。
确定哪一份具有规范效力，是本架构的前置条件，也是平台上任何常在线服务的前置条件。

### 6.2 没有协议层价格 oracle —— **对永续合约阻塞**

> no consensus-layer oracle dependency is introduced in v3. A future CIP MAY re-peg once
> an oracle module exists.
> —— CIP-2 v3

Hyperliquid 的 oracle（#8）位于共识内部：验证者发布，协议聚合。Cowboy 没有等效模块，
且 CIP-2 v3 连为其自身的质押下限都未引入。可用的构造是 `VerificationMode::MajorityVote`
下的 Runner 作业，它按作业往返而非按块交付 mark price。现货交易可以容忍，
永续资金费与清算阈值不能。

平台上唯一 oracle 形状的原生原语是 CIP-21 的 timer 驱动 TWAP，它受 §7 所述的退役影响。

### 6.3 Sequencer 公平性是信任假设而非性质 —— **需如实披露**

Hyperliquid 对「谁决定订单优先级」的回答是共识决定，操纵它需要质押级别的攻击。
在本架构中，运营 Runner 的一方最先观察到订单流。可用的缓解手段均为局部：

- `VerificationMode::Deterministic` 要求 TEE **且**跨 Runner 字节一致的结果，
  延迟敏感的撮合器无法产出；
- `MajorityVote` 每个决定需付一次往返；
- `EconomicBond` 是由质押背书的单个受信 Runner —— 实务上的选择，但那是 bond 而非证明。

CIP-23 composite attestation 实质性地收窄了这一点：它能证明**正在撮合的是哪个二进制**，
但不能证明该二进制是按其所报告的顺序观察到订单的。

**这是本架构在结构上唯一弱于 Hyperliquid 之处，应当如实表述，而不应表述为等效保证。**

### 6.4 CBQS provider 无 bond 且不可重指派 —— **按现规格阻塞**

> Out of scope, requiring a future CIP: […] provider reassignment, provider staking or
> slashing […]
> —— CIP-39 §Goals

若以 CBQS stream 作为交易所的 sequencer，其 broker 即是单一的、无 bond 的一方，
且不新建 stream 便无法更换。对 CBQS 的设计目标（agent 协调）而言这是合理的 v2 范围决定；
对订单录入而言不是。要么该推迟的 CIP 落地，要么由撮合 Runner 自持入口、CBQS 仅承担扇出 ——
代价是失去按市场划分的 lane 模型。

### 6.5 at-least-once 投递；exactly-once 为明列非目标 —— **应用层工作**

> Not goals: […] exactly-once application side effects […]
> —— CIP-39 §Goals

被重投的订单不得成为第二笔成交。这是应用层标准的幂等键工作，完全可解；
之所以记录，是因为它在设计阶段做进去成本很低，而事后发现则是一起正确性事故。

相关：CBQS 的 lane 共享同一条 stream 的吞吐，一条热 lane 会对兄弟 lane 施加背压。
除非为每个市场分配独立 stream，否则单一市场的异常行情会拖累其他市场。

### 6.6 没有原生永续或保证金原语 —— **在预期之内，但必须计入成本**

CIP-20 提供 `u128` 金额与校验 hook 的现货同质代币。仓位、杠杆档位、维持保证金、
资金费计提与社会化亏损均为需要编写的 actor 代码。这是正常的职责划分 ——
Hyperliquid 也是把同样的逻辑建进 HyperCore —— 但不应按「已提供」计入。

### 6.7 亚秒级用户可见最终性 —— **部分可挽回**

订单确认很快，因为它不触及链。结算最终性为一个块加结算窗口再加争议窗口（§9.5）。
对吃单方而言这与中心化场所相当；对任何需要已最终化抵押品方能行动的流程而言并非
Hyperliquid 等价物，应表述为一个有界窗口，而非表述为对等。

## 7. 与 CIP-21 / CIP-22 退役的相互影响

CIP-21（DEX 与流动性池）与 CIP-22（连续清算拍卖）计划在入口处停用，
实现保留但不可达。有两点后果与本架构相关，二者均不构成反对退役的理由。

1. **CIP-21 的 TWAP oracle 随之撤出。** CIP-21 §6.1 提供了平台上唯一 oracle 形状的原生原语
   （"Native TWAP oracles via timers, no external keeper"）。在入口处停用 CIP-21 会使 §6.2
   严格变差，因为替代架构比 AMM 更需要 mark price。应当明确重新指派 oracle 需求的归属，
   而不是让它随该 CIP 一同失效。
2. **HIP-1 与 HIP-2 的对应物失去平台原语。** CIP-22 提供了 ticker 拍卖（#11）所需的连续清算
   拍卖机制，CIP-21 提供了 HIP-2（#12）所需的自动流动性机制。停用之后二者均成为普通 actor
   代码 —— 可以接受，甚至可说是正确的，但在任何能力对比中，它们从**平台提供**移到了
   **应用自建**。

入口开关在两处都是恰当的机制。当一个模块存在广泛的内部耦合时，
仅对其单一入口（注册，或上市）设闸即可使其余部分不可达，无需删除实现。

## 9. 结算窗口尺寸

架构所倚赖的唯一一个定量问题。它可由协议的 gas 常量计算得出，结论是结算应当每块进行。
模型与出处见配套的 `settlement_window_model.py`。

下文全部常量读自 `node/types/src/constants.rs` 与 `node/execution/src/gas.rs`。

### 9.1 真正的约束是 cells，而非 cycles，亦非交易速率

§3 中的 50–150 TPS 在此是错误的量具。它计的是**交易笔数**，
而一个覆盖 1,700 个账户的结算批次是**一笔**交易。起支配作用的预算是每块 gas 目标：

| 预算 | 数值 | 性质 |
|---|---|---|
| `BLOCK_CELLS_TARGET` | 4,000,000 / block | EIP-1559 目标，无 lane 划分 |
| `BLOCK_CYCLES_TARGET` | 20,000,000 / block | EIP-1559 目标 |
| `LANE_RUNNER_CYCLES` | 8,888,888 / block | 结算若以 job result 到达则为**硬上限** |
| `LANE_USER_CYCLES` | 22,222,222 / block | Runner 若以交易提交则为**硬上限** |
| `MAX_BLOCK_TRANSACTIONS` | 5,000 | 不相关 —— 只发送一笔交易 |

cells 目标名义上是软的，稳态下则不是。`BASEFEE_MAX_CHANGE_DENOM = 96` 意味着持续超目标消耗
会使 basefee 以**每块 +1.042%** 复利上涨：

| 持续超目标 | basefee 倍数 |
|---|---|
| 1 分钟 | ×1.9 |
| 5 分钟 | ×22.4 |
| 10 分钟 | ×501.5 |

交易所无法运行在 cells 目标之上。**4M cells/block 是硬性稳态预算**，
其中只应认领一个比例 φ —— 链上还有其他用户。下文取 φ = 0.5。

### 9.2 编码方式的选择值 8.4 倍

一个被结算账户的表示方式几乎决定了一切：

| | **A —— 仓位存于 actor 状态** | **B —— 仓位表示为 CIP-20 余额** |
|---|---|---|
| 结算机制 | PVM actor 循环，每账户一次 `storage_write` | 原生 `token_batch` 系统指令 |
| Cells / 账户 | 64 calldata + **1,000 storage_write** + 64 transfer = **1,128** | 64 calldata + 64 transfer = **128** |
| Cycles / 账户 | 3,700 | 1,500 |
| 账户 / 块（φ = 0.5，USER lane） | **1,767**（cells 约束） | **14,771**（cycles 约束） |
| PVM 解释执行 | 每块 1,767 次解释执行循环迭代 | 无 —— 循环为原生 |

`storage_write_cells = 1_000` 对 `token_transfer_cells = 64`，是触及 actor 状态而非平台代币
状态的 **15.6 倍惩罚**。这是设计中最大的单一杠杆，其指向与整体架构一致：让 PVM 离开热路径。
编码 B 不是微优化 —— 它消除了唯一一个 wall-clock 成本未经测量的组件（§9.6）。

### 9.3 结论：一个块的窗口

在 W = 1 时不存在可利用的净额 —— 每笔成交触及两个账户，故链上负载为 `2 × fills/sec`。
可行性是一次除法：

| 编码 / lane（φ = 0.5） | 账户/块 | 可持续 fills/sec 上限 | fills/天 |
|---|---|---|---|
| A —— position-write，RUNNER 或 USER lane | 1,767 | **884** | 76,000,000 |
| B —— token-only，RUNNER lane | 5,882 | **2,941** | 254,000,000 |
| B —— token-only，USER lane | 14,771 | **7,386** | 638,000,000 |

作为参照，一个大型永续场所每日成交量级在 10⁶–10⁷ 笔。**即便编码 A 也超出它一个数量级，
且是在一秒结算、仅使用半个块 cell 预算的前提下。**

因此，促成更长窗口的净额分析并未被触发。将其运行以确定它**何时会被触发** ——
`B(W) = N·(1 − e^(−2FW/N))`，最小可行 W：

| 活跃账户 | fills/sec | 净额拐点 W\* | 最小可行 W |
|---|---|---|---|
| 5,000 | 100 | 25 s | **1 块** |
| 5,000 | 5,000 | 0.5 s | **1 块** |
| 50,000 | 1,000 | 25 s | **1 块** |
| 50,000 | 5,000 | 5 s | **1 块** |
| 50,000 | 20,000 | 1.2 s | 4 块 |

W 仅在 20,000 fills/sec 时离开 1 —— 约每日 17 亿笔成交，并非需要为之做设计预留的规模。

### 9.4 一个块的窗口同时也是风险最优，故不存在权衡

拉长结算窗口的通常理由是吞吐，而 §9.3 消除了它。其余每一项考量都指向同一方向：

- **在途敞口对 W 线性。** 若撮合 Runner 失效，W 秒的成交仅存在于 CBQS stream 中并须重放。
  W = 1 使链上状态与实际状态的偏离最小。
- **每批次固定成本可忽略。** 每笔结算交易 6,564 cells 与 65,500 cycles ——
  在 200 个账户的批次上不足 3% 开销，且不随规模增长。
- **拐点以下净额一无所获。** 低于 `N/(2F)` 时几乎每笔成交都触及一个新账户，
  故更长的窗口批到同样多的条目，只是把它们推迟了。

成本最低的方案与最安全的方案重合。因此该参数需要的是一个默认值，而非调优。

### 9.5 主导最终性的是争议窗口，而非结算窗口

最终化时间 = 结算窗口 + `DISPUTE_WINDOW_BLOCKS`（75）：

| W | 到最终化 |
|---|---|
| 1 s | **76 s** |
| 15 s | 90 s |
| 60 s | 135 s |

在 W = 1 时，**76 秒中有 75 秒是 CIP-2 的争议窗口。** 将 W 从 60 降至 1 可挽回 59 秒；
其余 75 秒是任何结算窗口选择都触及不到的。若 76 秒的最终化对产品不可接受，
应当重新审视的参数是争议窗口或验证模式。

### 9.6 仍有一个量需要实测

gas 模型为 `storage_write` 计 200 cycles，本分析为一次解释执行的循环迭代假设 2,000 cycles。
**二者均非 wall-clock 测量值。** 编码 A 要求在单次 PVM 调用内、每一个块、于一秒预算内完成
约 1,767 次解释执行迭代与 1,767 次 `storage_set` host call。现有 PVM 基准套件报告
`actor_dispatch` 约 1.1 ms —— 那是一整笔交易（含 VM 启动），无法刻画一个紧凑的
1,767 次 host-call 循环。

**采用编码 A 之前需要的 benchmark：** 一个 actor handler 循环 N ∈ {100, 500, 1000, 2000}
个条目，每条执行一次 `storage_set`，端到端测量。通过条件：N = 2000 时 p99 低于约 300 ms，
将块内其余时间留出。

**编码 B 不需要该 benchmark**，因为 `token_batch` 以原生方式执行。
这是选择 B 的更强理由，强于那 8.4 倍的 gas 节省。

现在即应记录 B 的两条约束。`token_batch` **拒绝带 hook 的代币**
（`TokenBatchHookedUnsupported`），故携带 CIP-20 合规 hook 的抵押品代币无法批量结算，
将退回编码 A。另外，B 的全有全无契约通过在任何写入之前模拟每一条腿来保证，
代价是每个不同账户一次余额读 —— 成本低（`storage_read_cells = 0`）但在 cycles 上并非免费。

### 9.7 建议

1. **结算窗口 = 1 个块（1 秒）。** 不做净额、无批处理延迟、在途敞口最小。
   仅在超过约 7,000 fills/sec 时重新考虑。
2. **将仓位编码为 CIP-20 余额（编码 B）**，使结算成为原生 `token_batch` 而非 PVM 循环 ——
   成本低 8.4 倍，并消除未经测量的 wall-clock 风险。
3. **以用户交易提交结算**，由 Runner 自身账户发出而非作为 job result：
   USER lane 提供 RUNNER lane 2.5 倍的 cycles，而在编码 B 下 cycles 是约束项。
4. **按 cell 目标的 φ = 0.5 做预算**，并对持续超目标消耗设置告警；
   §9.1 表明超额在数分钟内即成为自我惩罚。
5. **通过争议窗口而非结算窗口处理最终性问题**（§9.5）。
