# Homestead on CIP-39 v2: what went wrong, why, and how it was fixed

**Date**: 2026-09-03
**Status**: Engineering post-mortem
**Scope**: the `homestead-based-on-cip-39-v2` branch, from the port of the relay and
browser client (2026-09-02) to a working public deployment (2026-09-03).
**Companion**: `homestead/docs/devnet-bring-up.md` is the runbook this report explains;
`refs/analysis/2026-09-01_homestead_web_product_plan.zh.html` is the product plan it serves.

---

## 1. Summary

Homestead's web client was ported to CIP-39 v2, brought up on a live devnet, given a
workspace shell, put behind a public name, and taken from unusable to usable. Thirty
commits, and **twenty-six distinct defects, nearly all of which every unit test in the
repository passed through** (§7 indexes them).

That last number is the finding. This was not a project where the tests were missing —
webeditor ran 596 tests, collab-relay 210, and both were green through nearly every one of
these failures. The defects were all of a kind that a test written from the same
understanding as the code cannot see.

Measured start to end on the public deployment:

| | before | after |
|---|---|---|
| bytes moved, one load + one page switch | 43.75 MB | 0.29 MB |
| cold open, sidebar drawn | never (or 30 s+) | 1.1 s |
| cold open, page readable | 9.6 s | 2.9 s |
| switching pages | 12.6 s | ~1.4 s |
| a new page's text reaching another reader | frozen at one character, permanently | 4–8 s |
| console errors on a healthy page open | 3 | 0 |
| who can administer the workspace | anyone with the URL | a signed-in member |

Section 3 groups the defects by the *shape* of the mistake rather than by chronology,
because the shapes recur and the chronology does not.

---

## 2. The phases

1. **Port** (0902). Relay, shared crates and browser client rewritten against v2's wire:
   one delivery class, broker-assigned integer lane ids, `RecordHeaderV2` as AAD, and
   application-owned payload crypto because v2 removed platform encryption.
2. **Bring-up** (0903, first half). Chain, provider, stream, broker behind TLS, trust
   anchor, readiness ceremony, ACL, relay, browser — end to end on one machine.
3. **Shell**. The browser build could open exactly one document, named by a query
   parameter; the page tree, permissions and workspace were reachable only from the macOS
   app. Sidebar, tabs, toolbar, search, sharing and trash were added against the same
   Homestead actor the native client uses.
4. **Public origin**. Loopback plus port forwarding does not survive contact with a real
   browser. Everything moved behind one nginx vhost with a real certificate.
5. **Performance**. 43.75 MB and a ten-second stall per page.
6. **Delivery** (0903, second half). The last correctness defect, the security posture,
   the operational deadline, and the console noise.

## 3. The defects, by shape

### 3.1 A test that mirrors the implementation cannot see the implementation's mistake

**`recordHeader` wrote the lane id little-endian**; the spec says big-endian. Sealing and
opening used the same helper, so every round-trip test agreed with itself while every
record written was unreadable to every other party. The test helper mirrored the
implementation, so it could never have caught it.

**How it was solved.** Not by more tests of the same kind — by a vector taken from the
*Rust codec*, which is the other side of the contract. The general rule: an encoding is a
contract between two parties, and a test that only asks one of them is a test of nothing.

The same shape, twice more:

- **The snapshot head signature was three-way inconsistent.** Production signed over
  `keccak256` of the signing bytes (the CBQS-wide convention, done inside
  `verify_cbqs_signing_bytes_strict_v2`); the shared crate's hand-written
  `sign_head`/`verify_head` signed the raw bytes; and **the frozen cross-language vectors
  had been generated by the latter**. Vectors and TypeScript corroborated each other
  perfectly, and nothing the relay published could be verified by any reader. Two signing
  call sites are a breeding ground for this; they were collapsed into one.
- **The nonce was bound to a quantity unknowable at write time.** `payload_crypto` derived
  its nonce from `(lane_id, sequence)`, but `AppendRequestV2` is `{lane_id, payload}` — the
  sequence only comes back in `Appended{sequence}`. The writer had to substitute a local
  counter, so the reader, using the real sequence, could never open the record, and an AEAD
  failure looks exactly like corruption. Replaced with a random in-frame nonce under
  XChaCha20-Poly1305 (192-bit, so random nonces are safe).

### 3.2 Removing a specific mechanism is not removing the capability

An early conclusion written into the port plan — *"v2 deleted the chain proof, so we can
only trust the node"* — was **wrong**, and it would have cost the product its trust model.
v2 deleted only the CBQS-specific `CbqsChainProofBundleV1`. The generic
`FinalizedStateProofBundleV1` still exists, the node still serves
`POST /proof/finalized-state`, and `cowboy-protocol-light-client` still verifies it. The
CBQS stream record is ordinary actor storage under the Stream Registry (`0x17`).

**Rule extracted**: before concluding a capability is gone, look for the general mechanism
that replaced the specific one.

The mirror-image mistake was also present: **the relay called five endpoints v2's node does
not serve** (`GET /cbqs/broker-state` ×4, `GET /cbqs/chain-proof` ×1). Its tests were green
because the fake node implemented them in the v1 shape. Whether a client works is a
question to ask of *the callee's route table*, not of the caller's tests.

### 3.3 Failures that are silent by protocol design

These were the most expensive, because there is nothing to read.

- **A browser refuses a WebSocket's certificate silently.** No interstitial, because there
  is no navigation; the close code is 1006 whether the certificate was refused, the host was
  down, or the port was never forwarded. Every page in the product said "Couldn't connect to
  this page — try opening it again", which is the one remedy that can never work. Every
  harness in the repo ran with `--ignore-certificate-errors`, which is exactly the condition
  a real browser never has, so every check passed while nothing worked for anyone.
  **Solved** in three moves: a `no-cors` fetch that *does* distinguish "cannot connect" from
  "connected and refused"; a `/diagnose` page with no bundle and no dependencies that runs
  the checks in the person's own browser and prints copyable text; and finally by removing
  the question — the broker's socket moved behind the vhost that already has a real
  certificate, so no second certificate exists to refuse.
- **§11.2 credit: a subscription opens with zero credit and the broker then delivers
  nothing, silently**, because declining to deliver into no credit is the protocol working.
  A snapshotter that opens a subscription and forgets to grant is indistinguishable from one
  whose stream is idle.
- **`At(0)` names no record.** The §9.1 erratum moved the record origin to 1 and kept 0 as
  an exclusive lower bound, so an origin replay asking for `At(0)` is refused. The
  checkpoint's `first_sequence` is not the answer either — it bounds one batch, so starting
  there silently skips everything committed before it. The only way a client learns the real
  floor is §12's `CursorTooOld`, which carries it.
- **A dequeued frame that is then dropped.** `flushOutbound` took a frame off the session's
  queue and discarded it when the socket was not open. The session believes it sent the
  record; the only copy is gone; nothing reports anything.

### 3.4 The thing being measured was not the thing costing time

Every timing before the public deployment had been taken **on the server**, where 10 MB is
110 ms. From a browser, one page load plus one page switch moved **43.75 MB**:

- 41 MB was the CBQS chain proof, fetched **four times** — once per channel, per page. It is
  one immutable bundle per `(stream, checkpoint height)` and the URL names both, but it was
  discarded the moment each fetch settled; the in-flight map only collapsed *concurrent*
  fetches.
- 2.4 MB was the bundle's own HTML being downloaded as a font and thrown away. A catch-all
  route answered every unknown path with the bundle, and `/fonts/*` resolves inside the app
  bundle for the macOS WebView and to nothing on this server.

Holding the bundle was not enough on its own: **that fetch is also where a revoked reader
finds out**, so skipping it would move the refusal to a different stage. The fix keeps the
request and removes the bytes — `If-None-Match`, and the relay answers 304. HTTP caching
alone could not be relied on: RFC 9111 §3.5 forbids storing a response to a request that
carried `Authorization` without `must-revalidate`, and Chrome declined to store ten
megabytes anyway, which is its right.

And a **9.9-second gap in which nothing happened at all** turned out to be
`verifyPrunedOriginFallbackReadiness`: bootstrap awaited it and assigned the result to a
variable **assigned twice and read never**. The gate wants a native body that no browser
host ever supplies, so in a browser it could only ever fall to its own 10-second timeout and
answer `false` into nothing. The await was removed; the gate was left exactly as it is,
because wiring it to a consumer is a different change.

### 3.5 A cliff, not a slope

Three limits in this system do not degrade — they stop.

- **The page registry.** `api/pages/list` loaded the whole registry, and past about sixty
  pages the handler exceeded the actor's per-call cycle cap. The gateway turned that into a
  502 and **the workspace could not be opened at all** — including `api/delete`, the one
  call that would have made it smaller. The gateway's limits were already at 39M, close to
  the block maxima, so the knob was exhausted; and a gateway limit set *above* the block
  maxima refuses every write while reads keep working, which looks nothing like a limits
  problem. **Solved** on the client: the route had carried `limit`/`cursor` all along and
  nobody used them.
- **The snapshotter's connection.** §11.2 needs one subscription per lane and this broker
  admits 256 per connection, so a little over 130 pages puts it over the ceiling — and it
  does not degrade, it returns before subscribing to anything, so *no* lane is materialized
  and every page created from then on reads back empty. **Lanes are never reaped**: deleting
  63 pages through the actor left all 262 lanes in the registry. Currently mitigated by a
  message that says what it costs; the real fix (spanning connections) is outstanding.
- **The trust anchor.** See §3.7.

The registry cliff was reached in practice, and **by the test harness rather than by a
person**: each run of `converge.mjs` and `check-shell-e2e.mjs` left a page behind, and 64 of
the workspace's 71 pages were test litter. One harness already "cleaned up" — by *trashing*,
which leaves the page in the registry at full cost. Both now delete.

### 3.6 The defect that took the longest: a publish that strands its own tail

**Symptom.** A page created, typed into, and opened from a browser sharing no storage with
the writer failed to show the text about half the time. In its worst form the relay's
replica held exactly **one character**, and stayed there — across a relay restart, across a
full index reconciliation, and for as long as anyone waited.

This was chased four times and got worse three of them. Recording that honestly:

1. *Opening each lane at its own cursor anchor.* This is what the cursor's shape argues for.
   But sending an **unanchored** lane to the origin rebuilds a replica older than the head
   already published for it, which the store refuses. Half the time became **every** time.
2. *Treating a refused publish as non-fatal.* Fails for a reason worth knowing: reconnecting
   is what **clears** the refusal, because a new session verifies whatever checkpoint the
   broker offers next, while a session kept alive re-offers the same one forever.
3. *A client-side recovery* — a reader that opens a page emptier than the relay says it is
   replays from the origin instead of hydrating. Correct, and it helps a page that has been
   around for at least one snapshotter cycle. It cannot help the newest pages, because the
   relay's answer comes from the same index the snapshot came from and is exactly as stale.
   Its first version also read `surface.textContent` — and the loading veil's own message is
   text inside the surface, so it never saw an empty page, passed its tests, and did nothing
   at all in the app.
4. *Widening the recovery's window* from four seconds to past a publish interval, having
   measured that a new page reaches the relay's replica about eight seconds after it is
   typed. A check at four seconds could never have caught one.

**The actual cause**, found by instrumenting the write path and then following the records
downstream: a published generation is bound to the checkpoint position it was built under,
and **a position carries exactly one of them**. The second publish at the same position is
skipped — and skipped *forever*, because a checkpoint only advances when new records are
committed, and a document nobody is still typing in commits nothing. v2 establishes
coverage by *asking*, so one checkpoint's records arrive as a run of single-delivery passes,
and the timer-driven publish fired in the middle of one. Everything applied after that
publish was stranded permanently. Pages typed into earlier looked fine only because
unrelated later traffic moved the position and carried them out — which is exactly why this
read as flakiness rather than as a rule.

**The fix is one condition** (`may_publish`): a pass that took a frame may not publish. The
wake timer keeps it live, so a dirty replica gets a quiet pass within one publish interval
whether or not the stream ever says anything again.

**What the diagnosis actually required**, in order, because the wrong answer was available
at every step:
- an opt-in per-append trace in the client (`?cbqstrace=1`), which showed all 42 appends
  accepted and framed — clearing the writer;
- a histogram of appends *by lane*, because the first six entries were all awareness traffic
  on a previously-open page and reading only those suggested the document channel was never
  called at all;
- the relay's own log, which showed 24 checkpoint-covered batches arriving and then **four
  minutes of complete silence** — the shape of a component that has stopped, not one that is
  failing;
- reading the *older* rooms' content, which had converged completely. That is what turned
  "records are being lost" into "publication is being skipped", and it was one `curl`.

Two real defects were found and fixed along the way that turned out **not** to be the cause
— the double-open that discarded a `Y.Doc`, and `flushOutbound` dropping frames. Both are
genuine; neither changed the symptom. A comment written mid-chase attributing the symptom to
`flushOutbound` was corrected before commit.

### 3.7 An operational deadline disguised as a constant

The finalized-state proof a browser verifies carries **every block header between the pinned
anchor and the height being proved** — `fetch_history` walks them one at a time. Its size is
therefore not a property of what is proved, but of how old the anchor is: measured here at
**228 bytes per block**, at one block per second.

| anchor age | proof size |
|---|---|
| 1 hour | 0.8 MB |
| 1 day | 18.8 MB |
| 3.4 days | 64 MB — `MAX_FINALIZED_STATE_PROOF_BUNDLE_BYTES_V1` |

Past that bound the node cannot produce a proof at all and **every client stops working**.
Long before it, the deployment is already unusable: an anchor 14 hours behind made each
proof 8.6 MB and took the sidebar from 2 seconds to over 30. This is not a devnet quirk —
any CIP-39 v2 deployment pins an anchor at build time and its clients pay the distance from
it.

**Solved** by `homestead/scripts/rotate-trusted-checkpoint.sh`: self-throttled on the lag so
it is safe to run hourly from cron, `--check` reports without acting, and it stops at the
first failing step with the previous anchor still installed and the relay still running.
Two things it must do that are not obvious, both learned the hard way:

- **Stop the relay for the mint.** The node rate-limits `/proof/finalized-state` and the
  relay is its heaviest client, so the mint tool otherwise gives up with *"stayed
  rate-limited across every retry"*.
- **Address the relay with `pgrep -x`**, on the process *name*. A `-f` pattern naming the
  binary also matches the shell carrying the command that contains it, so `pkill -f` takes
  the caller down with the relay.

A rotation is a **five-part** operation — re-mint, rebuild the relay (the anchor is
build-time), regenerate `shell-config.json`, rebuild the bundle, restart — and missing any
one of them leaves the old anchor in force with no error. Missing the third produced a proof
size that did not move at all.

### 3.8 Deployment posture

`serve-demo.mjs` minted a **workspace-admin** token on every page load and injected it. That
was correct while it listened only on loopback; behind a public name it meant anyone who
could reach the URL was an admin — able to read every page, edit them, and add members.

Sign-in was written but **unreachable**: nothing put a client id into `shell-config.json`, so
`googleAvailable` was false on every deployment, and the panel reported "this deployment has
no sign-in configured". Two further faults kept it looking mis-configured rather than
not-ready: the GIS script arrives *after* the panel is drawn and nothing re-rendered, and
"no client id" and "the script has not arrived" were reported as the same thing when only
one of them is the operator's fault.

Now: the injection is opt-in (`?demo=1`, for harnesses that cannot complete a Google
sign-in), the bare editor keeps its injection because it has no sign-in UI at all, and a
visitor signs in for themselves.

### 3.9 Noise that hides signal

Every page open produced two console errors from fetching the comments lane's proof bundle,
which 404s because nobody has ever commented — a normal state reported as an error. And
every page switch produced a third: the CBQS driver logged `console.error` on *any* socket
close, including the one it had just asked for, and a close on a socket still completing its
handshake reports 1006 — indistinguishable in a console from a broker nobody can reach.
`fatal()` had always ignored these; only the log did not.

Unpublished lanes now answer **204**; a close we asked for is not logged. `check-shell`
against the public deployment reports no console problems at all.

## 4. What made this hard

Five recurring shapes, in rough order of how much time each cost.

1. **The failure had no error.** Silent by protocol (zero credit, 1006), silent by
   convention (an empty document is a legitimate document), or silent because the value was
   assigned and never read. Most of the elapsed time went to *producing an observable*, not
   to fixing anything.
2. **The test and the code shared an assumption.** Encoding mirrored in the helper; a fake
   node built to the caller's expectation; a fixture generated by the wrong signer; a
   content volume seeded so the fallback under test was never reached; a helper pinned while
   its call site went free. In every case the suite was green and the product was broken.
3. **The reproduction was itself unrepresentative.** Harnesses ran with
   `--ignore-certificate-errors`; timings were taken on the server; the harness that tested
   the workspace was also the thing filling it up. A measurement taken in the wrong place is
   worse than no measurement, because it is believed.
4. **Intermittency had a rule underneath it.** "Fails about half the time" was, in the end,
   deterministic: a publish landed mid-batch, and whether a page looked correct depended on
   whether *unrelated later traffic* happened to carry it out. Chasing the statistics rather
   than the mechanism produced three fixes that measured worse.
5. **The limits are cliffs.** A workspace does not slow down at sixty pages; it stops. A
   snapshotter does not publish fewer lanes past its ceiling; it publishes none. Anything
   that grows without being reaped — pages, lanes, the anchor's distance from the head — is
   a scheduled outage rather than a performance question.

## 5. Method notes

What worked, stated as practice rather than as narrative:

- **Pin an encoding against the other implementation**, never against a mirror of your own.
- **Ask the callee's route table** whether a client works.
- **Mutate the call site, not the helper.** Three unit tests around `may_publish` stay green
  when the call site is changed to pass `true`. They pin the predicate and nothing else; the
  evidence that the call site matters is a devnet A/B, and the runbook says so. The same
  shape appeared with `published_body`, where pinning the helper left the call site free.
- **Verify geometry in a real engine.** jsdom does not model a `display` rule outranking
  `[hidden] { display: none }` — the assertion passes with the guard removed *and* with it
  inverted. Measure `getBoundingClientRect` in a real browser instead.
- **When a fix makes it worse, say so and revert.** Four attempts at §3.6 did, and three of
  them are recorded in the runbook rather than in the code, which is where the fifth
  attempt's information came from.
- **Read the older instances of the failing thing.** Two rooms typed into an hour apart, one
  complete and one frozen, is the whole diagnosis in §3.6.
- **A component that goes silent has stopped, not slowed.** Four minutes of no log lines is
  a stronger signal than any error would have been.

## 6. Where it stands

**Working**: sign-in required, workspace tree, page open, editing, cross-browser convergence
in 4–8 s, search, share links, trash, one public origin with a real certificate, automatic
anchor rotation, no console errors. Suites green — webeditor 596, collab-relay 210.

**Outstanding**, in order of how hard they bite:

1. **The snapshotter is one connection**, so ~128 pages is a hard ceiling past which the
   whole workspace stops converging — worse than the 502 it replaced. Requires spanning
   connections.
2. **Lanes are never reaped** when a page is deleted, so the count toward that ceiling only
   grows.
3. **The actor's per-node ACL scan is still O(all pages)** on every `pages/list` call. The
   client's pagination moved the cliff; it did not remove it.
4. **UI**: move/reorder, icon picker, trash view, workspace switching, a comments entry
   point, keyboard shortcuts, a mobile sidebar, a resizable sidebar.
