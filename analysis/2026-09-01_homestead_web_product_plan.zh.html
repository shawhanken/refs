COWBOY · HOMESTEAD · 产品方案

Homestead Web 版

把「要装 DMG 才能看」的产品,变成「发条链接就能用」。

核心判断:Homestead 的编辑器今天已经是一个能在浏览器里跑起来的 Web 应用。缺的不是编辑器,是外壳、认证和托管。这份方案围绕已确认的核心卖点,给出边界、架构、三阶段路线和每阶段的验收判据。

依据 homestead@main 6b836c4 会议 2026-09-01 Slack #homestead 08-04→08-31

01方案一句话

方案

复用现有的 webeditor/(25 个模块、395 个测试、自带完整 CBQS 浏览器客户端),为它补一层 Web 外壳、一套浏览器认证和一个托管入口,分三阶段交付:可分享的只读页 → 可协作编辑的单页 → 完整 Web 工作区。

macOS 原生版继续存在,承担本地文件夹与本机 Agent 这两件浏览器做不到的事。Web 版不是它的替代,是它的入口。

02为什么是现在

会议给的理由

0901 会议把优先级说得很直白:客户要的是可展示的产品实体,不是 CIP 进度。原话两句 ——「你不能说我是过来吃龙虾的,我龙虾没有,我给你上盘牛蛙」、「都是视觉动物嘛,就是这个市场都是个视觉动物嘛」。

而今天要让人看到 Homestead,路径是:签名 → 公证 → 下载 DMG → 拖进 /Applications → 过 Gatekeeper → 登录 → 等工作区激活。这条链上任何一环出问题(8 月里 502、更新器报错、沙箱迁移都出过),演示就没了。

Web 版把这条链压成一步:发一个链接

对「视觉动物」型受众,这是投入产出比最高的一次形态改动 —— 不需要新功能,只需要换一个交付形态。

战略理由

会议定的定位是「Homestead 对 Cowboy 就像 CodeX 对 OpenAI」、「链上那一堆东西最后都得通过 Homestead 串起来」。一个只能装在 Mac 上的入口,承载不了「统一入口」这个角色 —— 覆盖面最大的入口形态是浏览器。

这是一次明确的范围翻案,要写进纪要

docs/homestead-v1-spec.md 白纸黑字把 web client 列为 v1 out of scope(与 Windows/iOS、按人头计价并列)。本方案主张把它移进范围,理由是上面两条。不要假装这是既定计划 —— 它推翻了一条已写下的决定,需要拍板。

03技术起点:比想象中近得多

这一节是本方案的支点。编辑器不需要重写,它今天就能在浏览器里跑。

已经是纯 Web 的部分

资产规模说明

04定位与边界

Web 版是什么

  • 入口与演示面 —— 发一个链接,对方在浏览器里看到、并能编辑真实文档
  • 协作面 —— 多人同时编辑、评论、分享,不要求对方装任何东西、不要求对方用 Mac
  • Cowboy 能力的展示窗 —— 链上工作区、CBQS 协作、CBFS 存储,在一个普通浏览器标签页里发生

Web 版不是什么(这些留给桌面版)

不做原因
本地 Markdown 文件夹作为真相源File System Access API 只有 Chromium 系支持,且授权模型与「文件即真相」的承诺不匹配。桌面版的核心差异化就在这里,不要稀释
本机 Agent(ACP / Codex 子进程)浏览器起不了子进程。要在 Web 上提供 Agent,只能是服务端托管的形态 —— 那是另一个产品决定,不在本方案范围
Keychain、应用内更新、app-scoped 书签平台能力,Web 上不存在也不需要
离线优先Yjs + IndexedDB 天然给了短时离线容错,但「离线可用」不作为 Web 版承诺

按已确认的核心卖点逐条对照。平移=复用现有代码;重做=功能保留但要新实现;不做=留在桌面版。

06架构:复用什么、新建什么

07三阶段路线

每阶段都要能单独拿出去演示,不做「憋大招」。

W1

可分享的只读 Web 页

把现有的 GET /s/:guid 从「无 JS 的服务端渲染」升级成真正的阅读体验。

  • 用编辑器的只读模式渲染,而不是服务端 Markdown 转 HTML —— 图片、表格、Mermaid、代码高亮与桌面版一致
  • 补上评论级公开链接的交互面:权限格里有 comment 级,但今天那个页面没有 JS,拿到评论权限的人无处可评。这是现成的缺口
  • 不需要登录、不需要放开 CORS(同源)、不触碰写路径
验收:把一篇带图片、表格和 Mermaid 的文档分享出去,对方在手机和桌面浏览器上都能正常阅读并留下评论;撤销链接后立即失效。
W2

可协作编辑的单页 Web

登录后打开一个已授权的页面,在浏览器里协作编辑。这一阶段交付的是核心卖点本身。

  • 浏览器 PKCE 登录,拿 Google ID token 调 actor
  • 复用 cbqs/bootstrap.ts 走完整流程:领票据 → 铸 StreamGrant → 直连 broker → 验证快照头 → hydrate
  • 放开 relay CORS(见 §08),这是本阶段的前置硬条件
  • 附件改走 relay /assets
  • 暂不做侧边栏和页树:通过 URL 直达单页
验收:两个不同浏览器、两个不同 Google 账号打开同一个 URL,同时编辑,互相看到光标与内容;各自刷新后内容仍在;其中一人被移出工作区后,下一次重连即被拒绝。
W3

完整 Web 工作区

补齐外壳,达到桌面版的功能面(本地文件夹与本机 Agent 除外)。

  • 侧边栏页树、多工作区切换、标签页、收藏、回收站、搜索
  • 成员与权限管理、分享管理、计费面板
  • Notion ZIP 导入(前端解析或服务端任务,二选一)
  • 文档内 AI:推理走服务端代理,凭证不进浏览器
验收:一个新用户从零开始 —— 登录、建工作区、导入一份 Notion 导出、邀请同事、共同编辑、分享出去 —— 全程只用浏览器。

08必须先解决的具体工作项

硬阻塞:relay 的 CORS 白名单

services/collab-relay/src/lib.rs:2505 的 ticket_cors_origin_allowed() 目前只放行三种来源:null(即 file://,桌面版 WebView 加载本地单文件页面时就是这个)、localhost、127.0.0.1。

任何部署在真实域名上的 Web 版,调 /ticket、/cbqs/session、/cbqs/chain-proof 都会被浏览器挡下。这三条恰好是拿到编辑权限的必经之路。改动本身很小(一个函数 + 一个配置项),但必须配置化而不是写死,且默认拒绝未知来源。

工作项阶段内容
relay CORS 可配置W2 前置把允许来源做成部署配置;默认拒绝;与现有 file:// 桌面路径共存
Web 外壳骨架W2→W3路由、布局、状态层。对应 Swift 的 10 个 Feature 域,但只需其中的云端部分
浏览器认证W2PKCE + state/callback 校验;token 存内存 + 短期会话,不落 localStorage
附件路径切换W2workspaceassets.ts 增加浏览器分支,走 relay /assets 能力 URL
构建产物拆分W1桌面版是 vite-plugin-singlefile 打成单文件内联(含 wasm 的 data URI);Web 版应改为常规多产物构建,否则首屏要拖一个巨大的 HTML
IndexedDB 缓存层W3替代 SQLite 页树缓存;注意桌面版已有「按授权作用域隔离缓存、撤权即隔离」的规则,Web 版必须照抄
Notion 导入迁移W3NotionImport.swift 的解析与规划逻辑要么移植到 TS,要么做成服务端任务
别忘了刚合入的那条安全改动

relay 的 WebSocket 中继在 2026-09-01 刚加了 Origin 校验与连接数上限(node#1460)。Web 版部署时,这个校验和上面的 CORS 白名单是两处独立的来源判断,必须一起配置,否则会出现「HTTP 通了但 WebSocket 被拒」的半通状态。

09风险与待决

风险

风险说明与对策
稀释桌面版的差异化桌面版的卖点是「文件即真相 + 本机 Agent」。Web 版若也宣称本地能力,两边都说不清。对策:边界写死在 §04,对外话术统一为「Web 是入口,桌面是工作台」
信任边界扩大浏览器里跑 = 更大的攻击面(XSS、token 泄漏、第三方脚本)。对策:严格 CSP、token 不落持久存储、公开页保持 default-src 'none'
协作耐久性尚无证据目前还没有「数据在集群上确实持久」的证据(快照器已发布 generation 数曾为零)。Web 版会放大这个风险 —— 用户不会觉得「网页丢了内容」是可接受的。W2 上线前必须先有耐久性证据
与 CIP-39 v2 改造撞车当前所有研发在 homestead-based-on-cip-39-v2 分支,协作传输层正在改。Web 版复用的正是 cbqs/ 客户端。对策:W1 不碰传输层可以并行;W2 应排在 v2 传输稳定之后

待决

  1. 是否翻案 v1 spec 的「web client out of scope」? 这是本方案的前提,需要拍板。
  2. Web 版是免费入口还是付费产品的一部分? 影响计费面板要不要进 W3。
  3. Web 上要不要提供 Agent? 若要,是服务端托管形态,是一个独立产品决定。
  4. 域名与部署形态 —— 独立 origin 还是挂在现有 relay 主机下?影响 CORS 配置的复杂度。

10成功判据

一句话判据

把一个链接发给一个没有 Mac、没装过任何东西的人,他能在浏览器里打开文档、和你同时编辑、刷新后内容还在。

分解到三阶段:

  • W1 —— 分享出去的页面在手机浏览器上读起来和桌面版一样好
  • W2 —— 两个浏览器同时编辑同一页,光标互见,撤权后立即失效
  • W3 —— 一个新用户全程只用浏览器完成:登录 → 建工作区 → 导入 Notion → 邀请同事 → 协作 → 分享

另外两条不写进阶段但要一直盯:首屏时间(桌面版的预算是暖开 300ms / 冷开 1.5s,Web 版要给出自己的数字并实测)、没有一次内容丢失。
